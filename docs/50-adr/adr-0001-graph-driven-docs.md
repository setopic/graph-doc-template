# 設計文書をグラフとして管理する

- 日付: 2026-08-14
- 状態: stable

## 背景

設計文書が増えると、次の3つが同時に起きる。

1. どこに何が書いてあるか分からなくなる
2. 上流（ドメイン）を変えたとき、下流（ユースケース・API）が追従していないことに気づけない
3. 人もAIも、文書どうしの前提関係を毎回読み直して推測する

目次を手で整えても、2と3は解決しない。**前提関係そのものを、機械が読める形にする**必要がある。

## 決定

設計文書を、1つの文書を1つのノード、フロントマターの型つきリンクをエッジとするグラフとして管理する。
リンク切れ・孤立ノード・循環依存・層の逆流は、CIで検証する。検証に落ちる変更はマージしない。

## 理由

追従していない文書は、エッジの整合性として機械で検出できる。人のレビューに頼らなくてよい。

依存の向きを層で制限すると、設計の乱れをレビューの前に検出できる。

ノードとエッジが明示されていれば、AIに渡す文脈を、そのノードと近傍に絞れる。
全文書を読ませるより正確で、費用も安い。

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| 目次ファイルを手で整える | 更新漏れを検出できない。文書が増えるほど、目次が実態とずれていく |
| WikiやNotionに置く | 差分のレビューがしにくく、CIで検証できない |
| 汎用のリンクチェッカーだけを使う | リンク切れしか見ないので、層の逆流や循環は検出されない |
| グラフDBに文書のメタデータを入れる | MarkdownとDBの二重管理になる。文書自体を正とするべきである |

## 見直しの条件

ノード数が300を超えて、検証やレビューが実務の速度に追いつかなくなったら見直す。
層の定義（10/20/30/40）が、プロダクトの構造と合わなくなったときも見直す。
