# 設計文書をグラフとして管理する

- 日付: 2026-08-14
- 状態: stable

## 背景

設計文書が増えると、次の 3 つが同時に起きる。

1. どこに何が書いてあるか分からなくなる
2. 上流（ドメイン）を変えたとき、下流（ユースケース・API）の追従漏れに気づけない
3. 人も AI も、文書間の前提関係を毎回読み直して推測する

目次を手で整備しても 2 と 3 は解決しない。**前提関係そのものを機械可読にする**必要がある。

## 決定

設計文書を「1 文書 = 1 ノード、フロントマターの型つきリンク = エッジ」のグラフとして管理し、
リンク切れ・孤立ノード・循環依存・層の逆流を CI で検証する。
検証に落ちる変更はマージしない。

## 理由

- 追従漏れは「エッジの整合性」という機械的な形に落ちる。人のレビューに頼らなくてよい
- 依存の向きを層で縛ると、設計の崩れがレビュー前に検出できる
- ノードとエッジが明示されていれば、AI に渡す文脈を「そのノードと近傍」に絞れる。
  全文書を読ませるより正確で、安い

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| 目次ファイルを手で整備する | 更新漏れを検出できない。増えるほど劣化する |
| Wiki / Notion に置く | 差分レビューが弱く、CI で検証できない |
| 汎用のリンクチェッカーだけ使う | リンク切れしか見ない。層の逆流や循環は素通りする |
| グラフ DB に文書メタデータを入れる | Markdown と DB の二重管理になる。文書自体が正であるべき |

## 影響

- [[META-01]]: 規約とルール ID を定義し、CI の検証内容と一対一で対応させる
- [[ARCH-01]]: アーキテクチャ変更はこの ADR の仕組みに乗せて記録する
- 新しい文書は `python -m tools.graph new` で起こす。手で作ると採番と配置を間違える

## 見直しの条件

- ノード数が 300 を超えて、検証やレビューが実務の速度に追いつかなくなったとき
- 層の定義（10/20/30/40）がプロダクトの構造と合わなくなったとき
