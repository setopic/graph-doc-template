# ワーカーの実行モデル

> これは`refines`の使い方を示すサンプルノードである。
> [ARCH-01](./arch-01-sample-system-overview.md)の「構成」表にあるワーカーの行が長くなったので、その部分だけを切り出した。
> もともと1つの文書だったものを分けたので`refines`を使う。依存ではないので`depends_on`は使わない。
> 判断の基準は[META-01](../00-meta/graph-rules.md)にある。

## 責務

時間のかかる処理を、要求元の応答を待たせずに実行し、結果を書き戻す。

| 行うこと | 行わないこと |
| --- | --- |
| キューから要求を取り出して処理する | 利用者との直接のやりとり |
| 処理結果をデータストアに書き戻す | 業務ルールの最終判断（親の境界どおり） |
| 失敗した要求を再実行可能な形で残す | 要求の受け付け |

## 実行の流れ

1. APIサーバが要求を永続化し、キューに入れる
2. ワーカーが要求を取り出す
3. ワーカーが処理し、結果を書き戻す
4. 要求の状態を「完了」または「失敗」に更新する

要求と結果はどちらも永続化されているため、ワーカーが途中で止まっても要求は失われない。

## 再実行の安全性

**同じ要求を2回処理しても結果が変わらないこと**を、ワーカーを実装するときの条件とする。
これは、[ARCH-01](./arch-01-sample-system-overview.md)が前提に挙げている冪等性を、具体的な要求にしたものである。

結果の書き戻しは、要求IDをキーにした上書きにする。処理の途中で、外部に副作用を出さない。
出す必要が生じたら、この文書を見直す。

## 失敗の扱い

| 失敗の種類 | 扱い |
| --- | --- |
| 一時的な失敗（接続が切れたなど） | キューに入れ直して再実行する |
| 恒久的な失敗（入力が不正） | 再実行せず「失敗」として残し、理由を記録する |

上の表は、失敗の種類を区別できたときの扱いである。区別できない失敗は、一時的な失敗として扱う。
その結果、恒久的な失敗を再実行することがある。処理が冪等であれば害はない。

## 未決事項

再実行の上限回数と、上限に達した要求の置き場所は、まだ決まっていない。
