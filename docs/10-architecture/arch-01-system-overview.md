# システム全体構成

> **これはサンプルノードです。** グラフの形と書きぶりを示すためだけに置いてある。
> 実プロジェクトでは中身を差し替えるか、削除して `python -m tools.graph new` で作り直す。

## 解決したい構造上の問題

利用者からの要求（予約の作成・確認）を受ける入口と、状態を保持する場所と、
時間のかかる処理を分離したい。分離しないと入口の応答時間が処理時間に引きずられる。

## 構成

| 要素 | 責務 | 責務でないこと |
| --- | --- | --- |
| API サーバ | 入力の検証、ユースケースの実行、永続化 | 長時間処理そのもの |
| データストア | 状態の保持と一意性の保証 | 業務ルールの判断 |
| ワーカー | 時間のかかる処理の実行と結果の書き戻し | 利用者との直接のやりとり |

ワーカーの記述が長くなったので、詳細は [[ARCH-02]] に分けた（`refines`）。
**この文書は全体の見取り図として残す**。分割しても、ここを読めば構成は把握できる状態を保つ。

## 境界

- 利用者 ↔ API サーバ: HTTP / JSON。契約は `40-contracts/` のノードが正
- API サーバ ↔ ワーカー: キュー経由の非同期。要求と結果はどちらも永続化する
- API サーバ ↔ データストア: 同期。トランザクション境界はユースケース 1 件

## 前提と制約

- 同時実行の規模は 1 台の API サーバで賄える範囲（超えたらこの文書は無効）
- ワーカーの処理は再実行しても安全（冪等）であること
