# システム全体構成

> これはサンプルノードである。グラフの形と書き方を示すためだけに置いてある。
> 実際のプロジェクトでは中身を差し替えるか、削除して`python -m tools.graph new`で作り直す。

## 解決したい構造上の問題

利用者からの要求（予約の作成・確認）を受ける入口と、状態を保持する場所と、
時間のかかる処理を分けたい。分けないと、入口の応答時間が処理時間の分だけ延びる。

## 構成

| 要素 | 責務 | 責務でないこと |
| --- | --- | --- |
| APIサーバ | 入力の検証、ユースケースの実行、永続化 | 時間のかかる処理そのもの |
| データストア | 状態の保持と一意性の保証 | 業務ルールの判断 |
| ワーカー | 時間のかかる処理の実行と結果の書き戻し | 利用者との直接のやりとり |

ワーカーの記述が長くなったので、詳細は[ARCH-02](./arch-02-sample-worker-execution-model.md)に分けた（`refines`）。
この文書は全体の見取り図として残す。分割したあとも、ここを読めば構成が分かる状態を保つ。

## 境界

| 境界 | 方式 | 補足 |
| --- | --- | --- |
| 利用者とAPIサーバ | HTTPとJSON | 契約は`40-contracts/`のノードを正とする |
| APIサーバとワーカー | キューを経由する非同期 | 要求と結果はどちらも永続化する |
| APIサーバとデータストア | 同期 | トランザクションの境界はユースケース1件 |

## 前提と制約

同時に実行される規模が、1台のAPIサーバで賄える範囲にあること。超えたら、この文書は無効になる。
**無効になったと判定できる形で書く**（例: 秒間50要求、応答時間の95パーセンタイルが300ミリ秒）。
「賄える範囲」とだけ書くと、無効になったかどうかを誰も判定できない。

ワーカーの処理は、再実行しても安全（冪等）であること。
