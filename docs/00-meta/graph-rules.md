# グラフの規約

設計文書をグラフとして扱うための規約である。どの規約も、`python -m tools.graph check`で機械が検証できる形にしてある。検証結果には必ずルールID（G0xx）が出るので、エラーが出たらこの文書でそのIDを引く。

## 1. ノード

1つのMarkdownファイルが1つのノードになる。ファイルの先頭には、必ずフロントマターを置く。

```yaml
---
id: UC-01              # 必須。型ごとの接頭辞つき
type: usecase          # 必須。node-types.md の語彙
title: 予約を確定する    # 必須。一覧に出る名前
status: draft          # 必須。draft / review / stable / deprecated
tags: [booking]
depends_on:
  - DOM-01
related: []
---
```

フロントマターに使えるのは、YAMLのサブセット（スカラー・インラインリスト・ブロックリスト）だけである。ネストしたマップや複数行の文字列は使わない。

## 1.5 このグラフが扱えるもの・扱えないもの

このグラフは、設計文書（何を作るか）のための道具である。すべての文書に向くわけではない。運用手順を題材に試した結果、次のことが分かっている。

| 扱えるもの | 扱えないもの |
| --- | --- |
| 概念とその不変条件 | 手順の順序（1 → 2 → 3） |
| 前提と影響範囲の依存関係 | 時間の経過にともなう状態 |
| 境界をまたぐ契約 | 「この作業の次にこの作業」という作業の連続 |

### 順序はグラフに乗らない

`depends_on`は「これがないと成立しない」という意味で、「この後にやる」という意味ではない。手順の順序を表すエッジは用意していないので、順序は本文に書く。

配置手順や移行計画のように順序が重要な文書は、`usecase`層に置いたうえで、手順書用の雛形を使う。

```bash
python -m tools.graph new --type usecase --template usecase-runbook --id UC-02 --title "..."
```

### 層を無理に埋めない

題材によっては、ある層に書くことが本当に無いことがある。そのときは、空のままにするか、書けるものだけを書く。`10-architecture`の内容を言い換えて`20-domain`を埋めても、重複が増えるだけである。

特にドメイン層は「概念と不変条件」を求めるが、運用手順のような題材では、用語の定義までしか書けない。それは失敗ではない。その層が薄い題材だということである。

### checkが通ることの意味

`check`が見るのは、リンクの整合性と依存の向きだけである。次のことは見ていない。

| 見ていないこと |
| --- |
| 各層に十分な内容があるか |
| 雛形の項目が埋まっているか |
| ノードの中身が題材に合っているか |

**`check`が通っても、規約どおりに書けているとは限らない。** 題材と雛形が合っているかどうかは、人が判断する。

## 2. エッジ

エッジの書き方は、フロントマターと本文の2種類ある。意味を持つのは、フロントマターに書いたエッジだけである。

| 書き方 | 例 | 検証対象 |
| --- | --- | --- |
| フロントマター（型つき） | `depends_on: [DOM-01]` | リンク切れ・層・循環・成熟度 |
| 本文の相対リンク | `[DOM-01](../20-domain/dom-01-...md)` | リンク切れのみ |
| 本文の`[[ID]]`（書くときの略記） | `[[DOM-01]]` | リンク切れのみ |

本文に残す形は相対リンクである。`[[ID]]`はMarkdownの標準の記法ではないので、GitHub上ではただの文字として表示され、読み手はクリックできない。2つの形はどちらも同じ参照として扱われる。書くときは`[[ID]]`でよく、`linkify`が相対リンクに整形する。整形が最新かどうかはCIが確かめている。

```bash
python -m tools.graph linkify
```

コードブロック・コードスパン・HTMLコメントの中は書き換えない。規約や雛形に載せた書き方の例まで変換すると、例として使えなくなるからである。

### 本文リンクは層と循環の検査を受けない

これは意図して残した抜け道で、規約の穴でもある。本文には、下位層のノードから上位層のノードへの言及を書けてしまう。

```markdown
<!-- 層 30 のユースケースに、層 40 の契約への言及を書ける（検証は通る） -->
- [ ] 出力したファイルが文字化けしない（[[CON-02]]）
```

同じことをフロントマターの`depends_on`に書けば、`G007`で落ちる。本文に書くか`depends_on`に書くかは、次の基準で決める。

| 参照の性質 | 書く場所 |
| --- | --- |
| 前提 | `depends_on`に書く。層の逆流になるなら、設計に誤りがある |
| 補足の道案内（「詳細はこちら」程度で、消しても文書が成立するもの） | 本文に書く |

本文リンクが増えてきたノードは、`depends_on`に書くべきものが紛れていないかを点検する。

### リンクとして数えない場所

コードブロック（バッククォート3つで囲んだ範囲）、コードスパン（バッククォート1つで囲んだ範囲）、HTMLコメント（`<!-- -->`）の中にある`[[ID]]`や相対リンクは、リンクとして扱わない。規約や雛形に書き方の例を載せても、リンク切れにならないようにするためである。逆に言うと、コメントアウトした参照はグラフに現れない。

型つきエッジには、次の種類がある。

| 種類 | 意味 | 制約 |
| --- | --- | --- |
| `refines` | 分割元のノード。1つの文書を分けたときだけ使う | 同じ`type`同士のみ / 循環禁止 |
| `depends_on` | これが成立する前提となるノード | 層の逆流禁止 / 循環禁止 |
| `related` | 依存しないが、一緒に読むべきノード | 相互に書くこと（片側だけなら警告） |
| `supersedes` | この決定が置き換える過去の決定 | ADR同士のみ |
| `decides` | この決定が影響を与えるノード | ADRから張る |

### `refines`と`depends_on`の使い分け

同じ`type`同士では両方を書けてしまうので、基準を決めておく。**迷ったら`depends_on`を使う。** `refines`を使うのは、分割したときだけである。

| 問い | はい | いいえ |
| --- | --- | --- |
| その2つは、もともと1つの文書だったか（1つに戻せるか） | `refines` | `depends_on` |

```yaml
# ○ 分割: UC-03 が大きくなったので入口ごとに切り出した
# uc-09-...md
id: UC-09
title: ボタン経路で匿名投稿する
refines:
  - UC-03      # 親。共通の事前条件・事後条件は親が持つ

# ✗ 誤用: 匿名メッセージはロールの「一部」ではない。前提であって分割ではない
id: DOM-02
refines:
  - DOM-01     # ここは depends_on が正しい
```

分割するときは、親に全体の見取り図と共通部分を残す。親が空になるなら、それは分割ではなく置き換えである。その場合は`refines`を使わず、親のノードをなくす。

## 3. 層の向き

依存は、抽象度の高い側へ向ける。逆向きの依存は`G007`で落ちる。

```
40-contracts ──depends_on──▶ 30-usecases ──depends_on──▶ 20-domain ──depends_on──▶ 10-architecture
```

ドメインがユースケースを知っている状態は、設計の破綻である。そのため、規約で求めるだけでなく、検証で止める。ADR（`50-adr/`）とメタ文書は複数の層にまたがるので、層のルールの対象外にしている。

## 4. 到達可能性

すべてのノードは、[IDX-ROOT](../index.md)から辿れなければならない。

目次の一覧ブロックは`sync`が作り直す。同じディレクトリにあるノードをid順に並べるので、登録漏れも、改題したあとの古い題も残らない。手で書き足す必要はない。

```
<!-- graph:children:start -->   ← ここは sync が上書きする
<!-- graph:children:end -->
```

`sync`は、ブロックの外に書いた案内文には触らない。「困ったときに開くもの」のように手で選んだ一覧も、目次に置いてよい。

## 5. ルール一覧

| コード | 内容 | 直し方 |
| --- | --- | --- |
| `G001` | フロントマターが読めない / 必須キーが足りない | `id`・`type`・`title`・`status`を埋める |
| `G002` | `id`の重複 | 片方の番号を振り直す |
| `G003` | `id`の接頭辞・`type`の語彙・置き場所が合わない | [META-02](./node-types.md)の表に合わせる |
| `G004` | リンク切れ | 参照先の`id`を直すか、ノードを作る |
| `G005` | ルートの目次から到達できない | `sync`を回す（一覧ブロックを作り直す） |
| `G006` | 依存の循環 | どちらかを、共通の下位ノードに切り出す |
| `G007` | 層の逆流 | 依存の向きを反転させるか、下位層に概念を移す |
| `G008` | `refines`の種別が合わない | 同じ`type`同士にするか、`depends_on`にする |
| `G009` | `status`の語彙違反 / stableがdraftに依存している（警告） | 依存先を確定させるか、こちらを`review`に戻す |
| `G010` | `related`が片側だけ（警告） | 相手側にも`related`を書く |
| `G011` | 未確定のまま長期間放置されている（警告） | 確定させるか、削除する。意図して残しているなら、理由を本文に書く |
| `G012` | 参照されすぎている（警告） | 概念が混ざっていないかを点検し、必要なら分割する |
| `G013` | 依存先の旧称を使っている（警告） | 正しい用語に直す。旧称が別の意味で正しく使われているなら、旧称に挙げない |
| `G014` | テンプレートの必須の節が無い（警告） | 節を足す。書くことが無いなら「なし」と書く |
| `G015` | 依存先が変わったのに追従していない（警告） | 依存先の変更を見て、追従が要るかを確かめる。要らなければそのままでよい |
| `G016` | `implemented_by`の指し先が存在しない | パスを直すか、宣言を外す |
| `G017` | 文書と実装の片方だけが変わった（警告） | もう片方を見て、追従が要るかを確かめる |
| `G018` | READMEの図がGitHubの描画上限に近い / 超えている | `graph.mk`に`README_GRAPH_ARGS = --aggregate`を置く |
| `G019` | Markdownの表が途中で切れている | 挟まっている段落や空行を、表の外へ出す |
| `G020` | 取り下げた決定を断りなく引いている（警告。READMEも見る） | 生きている決定に差し替える（経緯は書き足さない） |
| `G021` | 自動生成ブロックより後ろに本文がある | 本文をブロックの前へ移す |
| `G022` | 同じ用語が複数のドメインノードで定義されている（警告） | 同じ意味なら、定義を1か所に置き、ほかは定義元へリンクする。別の意味なら語を分ける |
| `G023` | 契約が「対応」に挙げたユースケースを`depends_on`に書いていない（警告） | `depends_on`に足す |

`G001`〜`G008`と`G016`は構造の誤りで、直さなければ文書として成り立たない。`G009`〜`G015`と`G017`・`G020`・`G022`・`G023`は健全性の警告で、承知のうえで放置してもよい。

`G018`は、上限に近づいていれば警告、超えていればエラーになる。超えた時点で、READMEの図はGitHub上で描画されていないからである。

`G019`と`G021`はエラーである。表が切れていれば、その行はGitHub上でただの文字列として表示される。自動ブロックの下に回った本文は、読む人に届かない。どちらも、承知のうえで放置してよい場合が無いので、警告にはしていない。

`check`は既定では、警告があっても失敗しない。`--strict`を付けたときだけ失敗する。

**CIでは、mainへのpushとPRで`--strict`を使う。** PRで落ちなければ、マージした後のmainも落ちない。以前はPRだけ緩めていたため、PRが緑のままmainが落ちた（1.22.0）。

PRの`--strict`は、`--since`を付けずに走らせる。こうすると変更の窓が空になるので、`G015`・`G017`（「見たか」を聞く警告）では失敗しない。この2つは、PRでは`--since`付きで一覧だけを出す。追従が要るかどうかは人が決める。

それ以外のブランチへのpushでは、警告を出すだけにして、書いている途中で止めない。警告は「直すべきだが、今すぐ使えなくなるわけではない」ものなので、PRを出す前に直せば足りる。

### G011: 放置された未確定ノード

`draft`か`review`のまま、`STALE_AFTER_DAYS`（既定は90日）を超えて更新が無いと警告する。

判定するのは「いつ`draft`になったか」ではなく、「最後に触られたのはいつか」である。書きかけでも手が入り続けているなら問題はなく、止まっていることが問題だからである。

日付はgitの履歴から取る。gitが無いかリポジトリではない場合、浅いクローンの場合、そのファイルがまだコミットされていない場合は、何も報告せずに検査を飛ばす。浅いクローンでは、全ファイルが同じ日付になって判定できない。誤検知よりも、検知しないほうを選んでいる。

CIで有効にするには、`actions/checkout`に`fetch-depth: 0`が要る。履歴を見せたくないときは、`check --no-history`で明示的に飛ばせる。

### G012: 参照されすぎているノード

`depends_on`で`MAX_INCOMING_DEPENDENCIES`（既定は8）を超えて参照されると警告する。

参照が集まるノードには、複数の概念が混ざっていることが多い。変更したときの影響範囲が広く、追従を確かめる手間が大きく増える。分割を考えるきっかけとして使う。

ただし、語彙の中心になるノードは、参照が多くて当然でもある。点検した結果これでよいと判断したなら、しきい値を上げるか、警告のまま放置してよい。

### G013: 依存先の旧称

**同じ意味なら、同じ用語で書く。** 言い換えを並べて防ぐことはしない。書く前に、ドメインの目次（`20-domain/index.md`）の「用語の一覧」で、その意味の語がすでに無いかを調べる。一覧は`sync`が各ドメインノードの用語表から作り、最新かどうかをCIが確かめている。手で集めた用語集と違って、検査のかからない写しにはならない。

`G013`が見るのは、そのうち文字列で確実に判定できる部分だけである。用語表の「旧称」の列には、改名して使わなくなった語を書く。その語が、そのノードに`depends_on`か`refines`で（間接にでも）繋がっている文書で使われていると、警告する。

| 用語 | 意味 | 旧称 |
| --- | --- | --- |
| 得点 | 当事者それぞれが取ったゴール数 | スコア（文字列だった頃の名前） |

旧称が無ければ空欄にする。たいていの語には旧称が無い。

#### 言い換えを並べない

1.19までは、この列を「使ってはいけない言い換え」と呼び、思いつく言い換えを並べていた。やめたのは、測った結果による（1.20.0）。

| 測ったもの | 結果 |
| --- | --- |
| 派生5つで言い換えを並べていた行 | 85行。注記から旧称と分かるのは3行だけ |
| 言い換えを持たない用語（最大の派生） | 74行中42行。並べ尽くせない |
| 「この語は禁止語に挙げない」という断り書き | 14か所。文脈で意味が変わる語ほど増える |
| 実際に使われている語を後から禁じた事故 | 4回 |

言い換えの一覧は、並べた語しか見つけられない。同じ意味を別の語で書く揺れは、書く前に用語の一覧を調べて防ぎ、書いた後は`review`の`A003`に見てもらう。紛らわしい語との違いは、「意味」の欄で説明する。

**古い列名の表も読み続ける。** 「使ってはいけない言い換え」の列は、今も`G013`が読んでいる。見出しが合わない表は用語表として読まないので、読むのをやめると、それを取り込んだ派生で、気づかないうちに検査が止まる。新しい列名に移すときは、見出しを「旧称」に改め、旧称でない語は「意味」の欄の説明へ移す。

繋がりは、間接のものも辿る。契約はユースケースを経由してドメインに繋がるので、直接の`depends_on`だけを見ると、契約が旧称を使っている場合をすべて見落とす。

末尾の丸括弧は、セル全体にかかる注記として扱い、警告に添える。注記には、改めた経緯を書いても、使ってよい条件（「入力欄の呼称としてのみ使う」など）を書いてもよい。

この検査は、語の意味までは分からない。そのため、次のような誤検知も出る。

| 誤検知の例 | 何が起きているか |
| --- | --- |
| 旧称が、別の概念の名前として正しく使われている | 改名で空いた語を、別の概念に渡した |
| 否定するために持ち出している | 「スコアという文字列では持たない」 |

だから警告にとどめている。警告が出たら、直し方は3通りある。

1. 本文の語を、正しい用語に直す
2. 用語表の側を直す。その語が別の意味で正しく使われているなら、旧称に挙げない。条件つきなら注記に書く
3. 足りない用語を足す。指しているものに名前が無いために、旧称を使ってしまっていることがある。その概念をドメインノードに定義する

`--strict`を使うなら、1〜3のどれかで警告をすべて消す必要がある。消さずに残すなら、`--strict`を使わない。

#### 上位層は検査されない

`10-architecture`は`20-domain`に依存できない。依存すると層の逆流になる。辿る辺が無いので、アーキテクチャ文書はドメインの用語表で検査されない。ADRとメタ文書も同じである。

それでも、用語としては従うこと。同じものを指しているなら、同じ語で書く。**ただし、これは規約であって、`G013`では確かめられない。** 書く前に用語の一覧を調べ、書いた後は`review`の`A003`に見てもらう。`A003`には全ドメインノードの用語と意味を渡してあるので、依存の向きに制限されない。

検査の範囲を広げる案を、実際のプロジェクト3件で測った。どの案も採れなかった。

| 案 | 増える件数 | そのうち妥当 |
| --- | --- | --- |
| 依存の逆向きも辿る | +2 | 1件。どの文書が検査されるかが偶然で決まる |
| `related`も辿る | +0 |  |
| グラフ全体を見る | +30 | 2件 |

「グラフ全体」の案が使えないのは、目次や規約の文書が「## 追加するとき」「層ルール」のような一般的な語を使うからである。ドメインの語彙とは関係なく、正しい文章が大量に当たる。逆向きの案では、たまたまドメインが依存しているアーキテクチャ文書だけが検査される。検査されるかどうかの境目に、意味が無い。

見出しと列名は、`schema.py`の`TERM_SECTION_HEADING`・`TERM_COLUMN`・`TERM_MEANING_COLUMN`・`TERM_OLD_NAME_COLUMNS`で差し替えられる。1文字の語は本文のどこにでも現れるので、検査の対象外にしている（`TERM_MIN_LENGTH`）。

#### 旧称を足すときは、先に本文を検索する

実際に使われている語を後から旧称にすると、正しい文章が大量に当たる。用語表に書く前に、その語がすでにどう使われているかを確かめる。

```bash
grep -rn "旧称にしたい語" docs/
```

自分の文書でその語を使っているなら、それは旧称ではなく、別の意味で正しく使っている語かもしれない。言い換えを並べていた頃に、実際にこの取り違えが起きた。「不戦勝」を禁じようとしたら、そのノード自身が別の意味で「不戦勝」を使っていた。

#### 依存が無いノードどうしの衝突はG022が見る

同じ語を別々の概念に使っていても、依存関係が無ければ、`G013`は検出しない。

実例として、総当たり形式とトーナメント形式が、「不戦勝」を別の意味で使っていた。片方は「相手がいない」、もう片方は「相手が来なかった」という意味である。この2つは兄弟で、互いに依存していない。そのため、どちらの用語表に書いても、相手には届かない。

**用語表どうしの重なりは、`G022`が見る。** 同じ語を2つのノードが定義していて、どちらも相手へリンクしていなければ警告する。本文での使い分けまでは見ない。同じ親を`refines`しているノードどうしは、特に語が重なりやすい。

#### 兄弟の旧称は、共通の依存元で衝突する

兄弟どうしには用語表が届かないが、両方に依存しているノードには両方の用語表が届く。そこでは、片方の正式な用語が、もう片方では使わない語になっていることがある。

言い換えを並べていた頃に、先ほどの2つの形式で実際に起きた。総当たり形式の用語表に「棄権の言い換えとして『不戦勝』を禁じる」と書いたところ、対戦表を作るユースケースが警告を受けた。そのユースケースは両方の形式を扱うので、両方に`depends_on`している。そこで「不戦勝」を使うのは正しい。トーナメント形式の正式な用語だからである。これも、言い換えを並べるのをやめた理由の1つである。

旧称でも同じことが起きうる。**改名で空いた語を、兄弟が正式な用語として使っているなら、旧称に挙げない。** 旧称を足す前に見るべき本文は、自分の依存元だけではない。兄弟ノードの用語表（用語の一覧で調べられる）と、その兄弟に依存しているノードの本文も見る。

```bash
python -m tools.graph render --format json --focus DOM-05 --depth 2
```

この衝突は、概念が分かれていることの表れでもある。同じ語を別の意味で使う2つの形式が両方とも必要なら、分割は正しかったことになる。

#### 部分一致であること

語の照合は単純な部分一致なので、長い語の中に短い旧称が含まれていると当たる。たとえば「参加」を旧称にすると、「参加コード」も当たる。

これは弱点であると同時に、用語の作り方への警告でもある。旧称を含む新しい用語を作れば、改めたはずの呼び名を引き継いでしまう。

### G014: テンプレートの必須の節

`type`ごとに決めた節が本文にあるかを見る（`schema.REQUIRED_SECTIONS`）。

```python
REQUIRED_SECTIONS = {
    "domain": ("定義", "不変条件", "用語"),
    "usecase": ("概要", "事前条件"),
}
```

中身までは見ない。確かめられるのは、見出しがあることだけである。だから「なし」と書いてあれば通るが、それでよい。このルールの役目は、書く場所を用意させることと、書かないと決めたことを明示させることにある。何を書くかは人が決める。

#### 雛形の全節を必須にしない

必須にするのは、それが無いと文書として成立しない節だけである。雛形には、書くことがあれば書く節も含まれている。

実際のデータで測ったところ、**雛形の全節を必須にすると、141ノード中50件（35%）が落ちた。** その多くは、意図した省略である。たとえば、ログを扱うドメインノードに「ライフサイクル」が無いのは、寿命の状態遷移が無いからである。大会のノードの場合は、「状態」という節に書いてあるので、「ライフサイクル」の節を持たない。

これは規約の「層を無理に埋めない」（1.5節）と同じ話である。節についても、埋めるために中身の無い見出しを作らせてはいけない。

既定値は、既存のノードのほぼすべてが実際に持っている節から決めてある。プロジェクトの語彙に合わせて書き換えてよい。

#### refinesの子には親の節を求めない

`refines`を持つノードは、1つの文書を分けたものなので、親が持つ節を繰り返さない。たとえば総当たり形式のノードに「定義」「属性」が無いのは、親の大会ノードが持っているからである。

`REQUIRED_SECTIONS_REFINED`に`type`があれば、そちらが使われる。

#### 契約層は検査していない

契約には、HTTPのAPI、チャットの操作、ファイル形式と、複数の形がある。実際のデータを見ると、90%以上のノードが持つ節は1つも無かった。最も多い「受け口の一覧」でも、13件中9件である。

共通の形が無いものに、共通の必須の節は置けない。そのため`contract`は空にしてある。形が固まってから足す。

### G015: 依存先が変わったのに追従していない

**このルールだけは、グラフの状態ではなく、変更の状態を見る。** 変更の窓の中で依存先（`depends_on`・`refines`）が変わり、依存元が変わっていないノードを挙げる。

窓は、既定では未コミットの変更である。そのため、書いている途中で役に立つ。

```bash
python -m tools.graph check
```

`--since`を付けると、窓を広げられる。窓は、その参照との分岐点から`HEAD`まで（作業ツリーも含む）になる。

```bash
python -m tools.graph check --since origin/main
```

`--no-history`を付けるか、gitのリポジトリでなければ、何も出ない。

#### なぜ「依存先のほうが新しい」で見ないのか

gitの最終更新日を比べて、依存先のほうが自分より新しいものを出せばよさそうに見える。しかし実際のデータで測ると、**4リポジトリ212ノード中47件（22%）が常に警告に当たった。**

中心的なノードは頻繁に触られるので、それに依存している側はいつも「古い」ことになる。これは文書が古びているのではなく、いつもの状態である。しかも一度出た警告は、依存元を書き換えるまで消えない。見たうえで変えなくてよいと判断しても、消えない。

見たいのは古びた文書ではなく、取りこぼしである。つまり、いま依存先を書き換えたのに、依存している側を見ていない状態である。これは変更の窓の中でしか意味を持たない。窓を閉じれば（コミットすれば）警告は消えるので、消えない警告が積み上がらない。

同じデータで、コミット1件あたりの件数は中央値が0〜7、最大が32だった。

#### 自動ブロックだけの変化は数えない

`graph:auto`の中身は`sync`が生成しているので、依存元が追従する余地が無い。自動ブロックだけが変わったファイルは、変更として数えない。数えると、`sync`を回すたびに警告が出る。

#### 直接の依存だけを見る

推移的には辿らない。DOM-01が変わったとき、DOM-01を`depends_on`しているUC-01は挙がる。しかし、UC-01にしか依存していないノードは挙がらない。

推移的に辿ると、1回の変更でグラフの大半が挙がり、一覧として役に立たなくなる。影響が遠くまで及ぶと考えるなら、`render --focus <ID> --depth 2`で自分で辿る。

#### 追従が要るとは限らない

依存先の変更が、依存元に関係しないことは多い。**このルールは「見たか」を確かめるもので、「直せ」という指示ではない。** 一覧を見て変えなくてよいと判断したなら、そのまま進めてよい。

規約の文章に「影響範囲を確かめる」と書いても、確かめたかどうかは記録に残らない。変更したその場で一覧を見せるところまでが、機械にできる仕事である。

### G016 / G017: 実装との対応

文書と実装を同じリポジトリに置く場合だけ使う。ノードのフロントマターに、その文書が規定している実装を書ける。

```yaml
id: DOM-07
type: domain
title: チーム
implemented_by:
  - tournament/teams.py
```

書かなければ何も起きない。文書だけのリポジトリでは1件も宣言されないので、`G016`も`G017`も出ない。用語表の「旧称」と同じ扱いである。

#### これはエッジではない

ソースファイルはノードではない。`implemented_by`は、層（`G007`）にも循環（`G006`）にも到達可能性（`G005`）にも関係しない、グラフの外への指し先である。

エッジにすると、実装ファイルを目次に登録するよう求められ、層の向きを問われ、`refines`を持てるのかと聞かれることになる。どの問いにも答えが無い。

#### G016: 指し先が存在するか（エラー）

本文の`[[ID]]`に対する`G004`と同じ役割である。指し先が消えても、文書はそのまま読めてしまう。機械が確かめないと、気づかないうちに実態とずれていく。

指せるのは、同じリポジトリの中のパスだけである。ファイルでもディレクトリでもよい。別のリポジトリの実装は指せない。

#### G017: 片方だけが変わっていないか（警告）

**`G015`を、文書と実装の境界にまたがらせたもの**である。見ているのは`G015`と同じく変更の窓の中だけで、文書と実装の両方が同じ窓に入っていれば、何も言わない。

警告は、どちらの向きにも出す。

| 変わったもの | 出るもの |
| --- | --- |
| 実装だけ | 「実装が変わった。文書の追従が要るかを確かめる」 |
| 文書だけ | 「この文書が変わったが、実装は動いていない。実装の追従が要るかを確かめる」 |
| 両方 | 何も出ない |

どちらが正しいかは、機械には分からない。実装の内部を整理しただけなら、文書は変わらない。先に文書を決めてから実装するなら、文書だけが変わる。`G015`と同じく「見たか」を確かめるルールで、「直せ」という指示ではない。

#### 粒度は実際のデータで決める

4リポジトリで測ったところ、**実装のコミットの95%（tournament）と100%（medieval-idle）が、文書のidをコミットメッセージで参照していた。** 参照されたidは97種と17種で、いずれもすべて実在した。文書と実装の繋がりはすでにあり、それを確かめる手段だけが無かった。

実装との対応の粒度は、層によって違う。

| 層 | 実装との対応 |
| --- | --- |
| ドメイン | ほぼ1対1（チーム → `teams.py`、エントリー → `entries.py`） |
| 契約 | 多対少。画面を作るモジュールが、すべての契約に共通で現れる |
| アーキテクチャ / ADR | 対応するファイルが無いことが多い。宣言しなくてよい |

### G018: READMEの図がGitHubの描画上限に近い

GitHubは、Mermaidの図をエッジ500本までしか描かない。超えると図が丸ごと消え、`Edge limit exceeded. 500 edges found, but the limit is 500.`という短い文言だけが残る。

上限は、図の中からは変えられない。`mermaid.initialize`の`maxEdges`はGitHub側の設定で、図に書いても安全のため無視される。自分でホストするHTMLなら上限を引き上げられる。そのため、全体図はPages側に置き、READMEには減らした図を置くのが基本である。

数えているのは、グラフではなく、READMEに実際に入っている図である。`--aggregate`や`--focus`で減らしていれば、その結果を数える。GitHubが描こうとするのも、その図だからである。

| 状態 | 深刻度 |
| --- | --- |
| `MERMAID_WARN_EDGES`（既定は450）未満 | 何も言わない |
| 450〜499 | 警告 |
| 500以上 | エラー（すでに描画されていない） |

**500ちょうどで、すでに描画されなくなる。** GitHubが返す文言が`500 edges found, but the limit is 500`で、その時点で図は消えている。

#### 直し方

`render --aggregate`を使い、型ごとに1つの箱へまとめる。ノードが何件あっても、箱は型の数だけ、エッジは「型 × 種別 × 型」の組み合わせの数だけになる。そのため、ノードが増えても図は大きくならない。

使うかどうかは、リポジトリごとに選ぶ。`graph.mk`に次の1行を置く。テンプレートは`graph.mk`を配らないので、競合しない。

```make
README_GRAPH_ARGS = --aggregate
```

そのうえで図を作り直す。

```bash
make readme
```

小さいリポジトリでは使わないこと。集約すると個別のノードが図から消える。上限まで余裕があるうちに使うと、図を縮める必要が無いのに、情報だけを失う。

### G019: Markdownの表が途中で切れている

Markdownの表は、ヘッダ行と区切り行（`| --- |`）で始まり、空行か本文で終わる。途中に段落や空行が入ると、そこから先の行は表ではなく、ただの文字列として描画される。

```markdown
| 用語 | 意味 |
| --- | --- |
| 形式 | 対戦の組み方 |

ここに段落を書いてしまった。
| 進行中 | 結果を入れている状態 |   ← この行はもう表ではない
```

これは`G018`と同じ形の問題である。グラフの検査はすべて通るのに、GitHub上の見た目だけが崩れる。実際に2件見つかった。

| どこ | 何が起きたか |
| --- | --- |
| READMEのコマンド表 | 案内文を行の間に挿し込んだため、以降の14行が本文として表示された |
| ドメインノードの用語表 | 段落3つを挟んだため、1行が表から取り残された |

**どちらも`check`は通っていた。** `G013`の用語表の読み取りは行単位なので、取り残された行も拾えていた。機械は困らず、読む人だけが困る。

#### 判定

`|`で始まる行は、直前の行も`|`で始まっていれば表の続きである。次の行が区切り行なら、正しい表の先頭である。どちらにも当てはまらない行を、切り離された行とみなす。

コードブロックの中は見ない。この規約自身が上に悪い例を載せているので、見ると自分の文書で落ちる。

段落を挟んだ2つの表は正しい。2つ目の表にも、ヘッダと区切り行があるからである。

#### 直し方

挟まっている段落や空行を、表の外へ出し、表を1つに繋げる。行ごとに補足を書きたいなら、セルの中に入れるか、表の後にまとめて書く。

### G020: 取り下げた決定を現在の根拠として引いている

本文が`deprecated`のノードを指していると警告する。

**問題は、参照していることではなく、現在の根拠として引いていることである。** 実際のデータでは、置き換え先のADRがすでに決まっているのに古いほうを指したままの文書が、ユースケース層と契約層に集中して残っていた。

```markdown
報告期限は締めである（[[ADR-0008]]）。   ← ADR-0008 は取り下げ済み
```

歴史として引くのは正当なので、エラーにはできない。「以前はXと書いていた（`ADR-0008`）」は正しい使い方である。そのため`G009`〜`G015`と同じ警告にして、承知のうえで放置できる形にした。

`G009`とは重ならない。`G009`は、`stable`なノードの`depends_on`だけを見る。`G020`は`status`を問わず本文のリンクを見るので、実際のデータで残っていたものは、ほとんど`G020`でしか出ない。

#### 判定

本文リンク（`[[ID]]`と`[題](./xxx.md)`の両方）の指し先が`deprecated`なら警告する。ただし、次の場合は警告しない。

| 警告しない条件 | 理由 |
| --- | --- |
| 確定した記録（既定では`stable`なADR） | 確定したADRは書き換えない。直せないものには警告しない |
| 自分が、連鎖上で指し先の置き換え先にあたる | 置き換えた側は、置き換えた相手を指すのが自然である |
| `index`ノード | 一覧は、取り下げたものも並べるのが役目である |
| 自分も`deprecated` | 歴史が歴史を引いている |
| 同じ段落の中で、置き換え先も指している | その場で断っている |

#### READMEも見る

READMEはノードではないが、決定を引く。`graph.nodes`だけを見ていた頃は検査がREADMEに届かず、READMEだけが古い状態を説明し続けることがあった。

7リポジトリで実測したところ、3つのREADMEが、取り下げ済みのADRを現在の根拠として引いていた。そのうち1つは、置き換え後の事実を古いまま述べていた（「3つのBotを同居」と書いていたが、置き換えた決定の題は「台数を問わない」だった）。**READMEはノードより読まれるのに、検査はノードより薄かった。**

判定はノードと同じで、違うのは2点だけである。

| | ノード | README |
| --- | --- | --- |
| 相対リンクの基準 | 自分のディレクトリ | リポジトリの根 |
| 「自分が置き換えた側」の免除 | 効く | 効かない（ノードではないので、idが無い） |

見るのは`README.md`だけである。`CONTRIBUTING.md`と`CLAUDE.md`は実測で0件だった。しかも`CLAUDE.md`は派生が共有しているので、テンプレート側の1件がすべての派生で警告になる。

自動生成の図は数えない。図はコードブロックの中にあり、判定の前に除かれる。

#### 確定した記録は対象にしない

ADRは、確定したら書き換えない。決定を変えるときは本文を直さず、新しいADRを起こす。古いADRに要るのは後継へのリンクだけで、本文を保守する必要はない。

したがって、確定したADRに「直してください」と言う指摘は、原理的に解消できない。直すこと自体が原則に反する。警告を出し続けても、`--strict`を通らなくするだけである。

確定前（`draft`・`review`）のADRは、対象に残す。まだ決めている途中なので、直してよい。境目は「ADRかどうか」ではなく、「確定した記録かどうか」である。

対象外にする種別は、`schema.py`の`IMMUTABLE_RECORD_TYPES`にある。既定は`adr`だけである。

**実際に検査の対象として残るのは、現在の設計を述べる層（`10-architecture`〜`40-contracts`）である。** これらの層は「いまどうなっているか」を書く場所なので、古い決定を指していたら、生きている決定に差し替える。

置き換え先は、連鎖を辿って求める。`ADR-0004` → `ADR-0006` → `ADR-0007`と置き換わったとき、`ADR-0004`の置き換え先は、`ADR-0006`と`ADR-0007`の両方である。現在の決定（連鎖の先端）を指すほうが、直接の置き換え先を指すより正しい。片方しか認めないと、「`ADR-0004`の時点」と「現在（`ADR-0007`）」を並べた表で警告が出る。

同じ理由で、連鎖の先にいる側は、さかのぼって引いてよい。`ADR-0007`が2つ前の`ADR-0004`を引くのは、「あちらはこう決めていた」と書いているだけである。直接の置き換え先を引くのと変わらない。

表の最後の条件（同じ段落の中で置き換え先も指している）が最も重要で、範囲を段落に絞ることに意味がある。この範囲は、7リポジトリで実測して決めた。

| 案 | 警告が出る引用箇所 |
| --- | --- |
| 段落の中で置き換え先を指していれば警告しない | 64 |
| 文書のどこかで指していれば警告しない | 本当に直すべき箇所を取りこぼした |

「文書のどこかにあれば足りる」にはしない。長い文書では、別の話題で置き換え先に触れているだけで警告が消え、本当に直すべき箇所を取りこぼす。

#### 直し方

生きている決定に差し替える。

```markdown
報告期限は締めではない（[[ADR-0014]]）。
```

経緯は書き足さない。「かつては`ADR-0008`に従うと書いていた」という記述は、この層には要らない。文書自身の履歴はgitにあり、決定の経緯はADR層にある。正しく直すと、取り下げたADRへの参照ごと消えて、文書が短くなる。

差し替えるには、どこまでが生きているかを知る必要がある。それは、置き換えた側のADRの「決定」にしか書かれていない。`adr.md`雛形の「決定」の案内で、置き換えるときに引き継ぐ範囲を書かせているのはこのためである。書いてあれば、置き換えた側のADRを1つ読むだけで、この警告を直せる。

歴史として引いていることが本当に必要なら、そのまま放置してよい。

### G021: 自動生成ブロックより後ろに本文がある

`sync`が書く自動生成ブロックの終わりより後ろに、空白以外の文字が残っていたら、エラーにする。

自動ブロックは「関連ドキュメント（自動生成 / 手で編集しない）」という、文書の締めである。読む人は、その下に本文が続くとは思わない。しかもCLAUDE.mdが「この塊を手で編集するな」と書いている。そのため、下の本文を直したい人は、「触るな」と書かれた塊を越えて行くことになる。

`sync`は、この状態を自分では直せない。ブロックがすでにあれば、その場で入れ替えるだけで、後ろに回った本文は動かさない。だから一度こうなると、誰も気づかないまま残り続ける。

**実際に、この文書（`META-01`）で84行が自動ブロックの後ろに落ちていた。** 5節のルール一覧から`G015`〜`G019`が切り離され、そのうち`G018`と`G019`は自動ブロックより下にあった。共有ファイルなので、7リポジトリすべてが同じ状態だった。1.14.2で直してある。

#### 判定

目印は`graph:auto:end`だけを見る。

目次の`graph:children:end`は見ない。一覧の後ろに「使い方」を書くのが目次の正しい形なので、そこを見ると目次がすべて落ちる。

ブロックが2つある文書はすでに誤った状態だが、最後のブロックを基準にする。間に挟まった本文まで数えると、直す場所が分からない指摘になる。

`sync`を一度も回していない文書（ブロックが無い文書）には、何も言わない。

#### 直し方

本文をブロックの前へ移す。ブロックは文書の最後に置く。

並べ替えたあとは、行の多重集合が元と一致することを確かめると安全である。一致すれば、本文を書き換えずに動かしただけだと言い切れる。

### G022: 同じ用語が複数のドメインノードで定義されている

ドメインノードの用語表どうしを比べ、同じ語を2つ以上のノードが載せていて、定義元が決まっていないときに警告する。

**同じ意味なら同じ用語で書き、定義は1か所に置く。別の意味なら語を分ける。** `G013`は依存の向きにしか届かない。そのため、兄弟ノードが同じ語を別の意味で定義していても、これまで誰も気づけなかった（`G013`の「依存が無いノードどうしの衝突」）。

意図して同じ語を載せた場合は、警告が出ない。ほかのノードの語を自分の表にも載せるときは、「意味」の欄から定義元へリンクする。

| 用語 | 意味 | 旧称 |
| --- | --- | --- |
| 試合形式 | 何試合行い、勝者をどう導くかの取り決め（`[DOM-10](./dom-10-game.md)`） |  |

同じ語を載せている行のうち、同じ語を定義している別のノードへリンクしていない行が1つだけなら、その行が定義元である。この場合、警告は出ない。リンクしていない行が2つ以上あれば、定義元が決まっていない。

1.20.0で実測した結果は次のとおりである。

| 派生 | 重複 | 警告が出る |
| --- | --- | --- |
| tournament-bot | 5（回戦数・試合形式・棄権・裁定・範囲） | 2（裁定・範囲。どちらも別の意味で2回定義されていた） |
| ほかの4つ | 0 | 0 |

警告が出たら、直し方は2通りある。

1. 同じ意味なら、定義を1か所に置く。ほかの行は「意味」から定義元へリンクするか、行ごと消して本文から定義元を指す
2. 別の意味なら、語を分ける。どちらかの語を変える

**リンクは「承知している」という印にすぎない。** `G022`は同じ意味かどうかまでは見ないので、リンクを張れば、別の意味でも警告が出なくなる。警告を消すためにリンクを張ってはいけない。それは検査を欺くことになる。

### G023: 契約が「対応」に挙げたユースケースをdepends_onに書いていない

規約では、契約ノードは、対応するユースケースを必ず`depends_on`に持つ。契約の雛形は、同じことを本文にも書かせる。片方だけを書き忘れると、そのユースケースを書き換えても、`G015`が契約を挙げない。`G013`も、ユースケースの先にある用語表を契約に当てない。本文のリンクは、リンク切れしか検査されない。

`G023`が読むのは、次の2か所だけである。どちらも、雛形が用意している書き場所である。

| 書き場所 | 雛形 |
| --- | --- |
| 見出しが「対応」で始まる表の列（対応・対応するユースケース・対応する例外フロー） | `contract` / `contract-interaction` |
| 「対応するユースケース:」の行 | `contract-http` |

本文の道案内のリンクは読まない。読むと、tournament-botだけで29件当たった。HTMLコメントの中（雛形の記入案内）も読まない。

「UC-25と同じ」のように振る舞いを借りている行も数える。借りたUCが、その振る舞いの仕様そのものになっているからである。実装が別なら、借りたUCが変わったときに、`G015`で契約を見に行けることに意味がある。

1.21.0で、入れる前に実測した。tournament-botでは4つの契約から10本、gacha-monitorでは2つの契約から2本が抜けていた。ほかの派生とテンプレートは0件だった。

UCの表を持たない契約（メッセージ・ファイル・環境変数の形式）は、比べるものが無いので対象外である。

## 6. 運用サイクル

1. `python -m tools.graph new --type usecase --id UC-02 --title "..."`でノードを作る
2. 本文と、フロントマターの`depends_on`を書く
3. `python -m tools.graph check`が通るまで直す
4. `python -m tools.graph sync`で、各文書の末尾の関連リンクを作り直す
5. コミットする（CIでも3と4を検証する）

まとめて作るときは、1行に1ノードを書いたファイルを渡す。

```bash
python -m tools.graph new --from docs/00-meta/new-nodes.txt
```

```
# type | id | title | slug | status | template
usecase | UC-02 | 予約をキャンセルする | cancel-booking
contract | CON-02 | キャンセル API | cancel-api | draft | contract-http
```

`slug`以降は省略できる。1件失敗しても残りは作られ、失敗した分だけが報告される。

## 7. 雛形

雛形は`00-meta/templates/`にあり、既定では`<type>.md`が使われる。同じtypeに複数の書式が要るときは、`--template`で選ぶ。

| 雛形 | 用途 |
| --- | --- |
| `contract.md` | 伝送方式に依存しない「境界をまたぐ約束事」。既定の雛形 |
| `contract-http.md` | HTTPのAPI。エンドポイントとステータスコードを持つ |
| `contract-interaction.md` | チャットの操作（コマンド・ボタン）。識別子が利用者の手元に残る |
| `usecase-runbook.md` | 人間が実行する手順（配置・更新・障害対応・移行） |

```bash
python -m tools.graph new --type contract --template contract-http --id CON-02 --title "..."
```

雛形そのものは、グラフに含めない（`EXCLUDE_PREFIXES`で除外している）。そのため、`{{ID}}`のような置き換えていない記述が残っていても、検証には出ない。
