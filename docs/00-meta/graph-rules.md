# グラフの規約

設計文書をグラフとして扱うための規約。**すべて `python -m tools.graph check` で機械検証できる**
形にしてある。ルール ID（G0xx）は検証結果に必ず出るので、エラーが出たらここを引く。

## 1. ノード

- 1 つの Markdown ファイル = 1 ノード。
- 先頭に必ずフロントマターを置く。

```yaml
---
id: UC-01              # 必須。型ごとの接頭辞つき
type: usecase          # 必須。node-types.md の語彙
title: 予約を確定する    # 必須。一覧に出る名前
status: draft          # 必須。draft / review / stable / deprecated
tags: [booking]
depends_on:
  - DOM-01
related: []
---
```

フロントマターは YAML のサブセット（スカラー・インラインリスト・ブロックリスト）のみ。
ネストしたマップや複数行文字列は使わない。

## 1.5 このグラフが扱えるもの・扱えないもの

**設計文書（何を作るか）のための道具**であり、すべての文書に向くわけではない。
運用手順を題材に試した結果、次のことが分かっている。

| 扱えるもの | 扱えないもの |
| --- | --- |
| 概念とその不変条件 | **手順の順序**（1 → 2 → 3） |
| 前提と影響範囲の依存関係 | 時間の経過にともなう状態 |
| 境界をまたぐ契約 | 「この作業の次にこの作業」という作業の連続 |

### 順序はグラフに乗らない

`depends_on` は「**これがないと成立しない**」であって「この後にやる」ではない。
手順の順序を表すエッジは用意していない。**順序は本文に書く。**

順序が重要な文書（配置手順、移行計画など）は、`usecase` 層に置いたうえで
手順書用の雛形を使う。

```bash
python -m tools.graph new --type usecase --template usecase-runbook --id UC-02 --title "..."
```

### 層を無理に埋めない

題材によっては、ある層に書くことが本当に無いことがある。
そのときは**空のままにするか、書けるものだけ書く**。
`10-architecture` の内容を言い換えて `20-domain` を埋めても、重複が増えるだけ。

特にドメイン層は「概念 + 不変条件」を求めるが、運用手順のような題材では
**用語の定義までしか書けない**。それは失敗ではなく、その層が薄い題材だということ。

### check が通ることの意味

`check` が見るのは**リンクの整合性と依存の向き**だけ。次のことは見ていない。

- 各層に十分な内容があるか
- 雛形の項目が埋まっているか
- ノードの中身が題材に合っているか

**通ったことは「規約どおりに書けている」ことを意味しない。**
題材とテンプレートが合っているかどうかは、人が判断する。

## 2. エッジ

エッジは 2 種類の書き方がある。**意味を持つのはフロントマターの側だけ。**

| 書き方 | 例 | 検証対象 |
| --- | --- | --- |
| フロントマター（型つき） | `depends_on: [DOM-01]` | リンク切れ・層・循環・成熟度 |
| 本文の相対リンク | `[DOM-01](../20-domain/dom-01-...md)` | リンク切れのみ |
| 本文の `[[ID]]`（書くときの略記） | `[[DOM-01]]` | リンク切れのみ |

**本文に残す形は相対リンク。** `[[ID]]` は Markdown の標準記法ではないので、
**GitHub 上ではただの文字として出る**（読み手はクリックできない）。
両方とも同じ参照として扱われるので、**書くときは `[[ID]]` でよく、
`linkify` が相対リンクに整形する。** CI が最新かどうかを見ている。

```bash
python -m tools.graph linkify
```

**コードブロック・コードスパン・HTML コメントの中は書き換えない。**
規約や雛形に載せた「書き方の例」まで変換すると、例として成立しなくなる。

### 本文リンクは層と循環の検査を受けない

これは意図的な逃げ道であり、**規約の穴でもある**。本文には、下位層のノードから
上位層のノードへの言及を書けてしまう。

```markdown
<!-- 層 30 のユースケースに、層 40 の契約への言及を書ける（検証は通る） -->
- [ ] 出力したファイルが文字化けしない（[[CON-02]]）
```

同じことをフロントマターの `depends_on` に書けば `G007` で落ちる。使い分けの基準は次のとおり。

- **前提**なら `depends_on` に書く。層の逆流になるなら、それは設計が壊れている合図
- **補足の道案内**なら本文に書く。「詳細はこちら」程度の参照で、消しても文書が成立するもの

本文リンクが増えてきたノードは、`depends_on` に書くべきものが紛れていないか点検する。

### リンクとして数えない場所

次の中にある `[[ID]]` や相対リンクは、リンクとして扱わない。

- コードブロック（バッククォート 3 つで囲まれた範囲）とコードスパン（`` ` `` で囲まれた範囲）
- HTML コメント（`<!-- -->`）

規約や雛形に「書き方の例」を載せてもリンク切れにならないようにするため。
逆に言うと、**コメントアウトした参照はグラフに現れない**。

型つきエッジの種類:

| 種類 | 意味 | 制約 |
| --- | --- | --- |
| `refines` | **分割元**のノード。1 つの文書を分けたときだけ使う | 同じ `type` 同士のみ / 循環禁止 |
| `depends_on` | これが成立する前提となるノード | 層の逆流禁止 / 循環禁止 |
| `related` | 依存しないが併読すべきノード | 相互に書くこと（片側だけなら警告） |
| `supersedes` | この決定が置き換える過去の決定 | ADR 同士のみ |
| `decides` | この決定が影響を与えるノード | ADR 起点 |

### `refines` と `depends_on` の使い分け

同じ `type` 同士では両方が書けてしまうので、基準を決めておく。
**迷ったら `depends_on`。** `refines` を使うのは分割したときだけ。

| 問い | はい | いいえ |
| --- | --- | --- |
| その 2 つは、もともと 1 つの文書だったか（1 つに戻せるか） | `refines` | `depends_on` |

```yaml
# ○ 分割: UC-03 が大きくなったので入口ごとに切り出した
# uc-09-...md
id: UC-09
title: ボタン経路で匿名投稿する
refines:
  - UC-03      # 親。共通の事前条件・事後条件は親が持つ

# ✗ 誤用: 匿名メッセージはロールの「一部」ではない。前提であって分割ではない
id: DOM-02
refines:
  - DOM-01     # ここは depends_on が正しい
```

分割するときは、**親に全体の見取り図と共通部分を残す**。親が空になるなら、
それは分割ではなく置き換えなので `refines` は使わず、親のノードを畳む。

## 3. 層の向き

依存は **抽象度の高い側へ向ける**。逆向きは `G007` で落ちる。

```
40-contracts ──depends_on──▶ 30-usecases ──depends_on──▶ 20-domain ──depends_on──▶ 10-architecture
```

ドメインがユースケースを知っている状態は設計の破綻なので、規約ではなく検証で止める。
ADR（`50-adr/`）とメタ文書は横断的なので層ルールの対象外。

## 4. 到達可能性

すべてのノードは [IDX-ROOT](../index.md) から辿れること。

**一覧ブロックは `sync` が作り直す。** 同じディレクトリにあるノードを id 順に並べる
ので、登録漏れも改題の取り残しも起きない。手で書き足す必要はない。

```
<!-- graph:children:start -->   ← ここは sync が上書きする
<!-- graph:children:end -->
```

**この外に書いた案内文には触らない。** 「困ったときに開くもの」のような
手で選んだ一覧を目次に置いてよい。

## 5. ルール一覧

| コード | 内容 | 直し方 |
| --- | --- | --- |
| `G001` | フロントマターが読めない / 必須キー不足 | `id` `type` `title` `status` を埋める |
| `G002` | `id` の重複 | 片方を採番し直す |
| `G003` | `id` 接頭辞・`type` 語彙・置き場所の不一致 | [META-02](./node-types.md) の表に合わせる |
| `G004` | リンク切れ | 参照先の `id` を直すか、ノードを作る |
| `G005` | ルート目次から到達できない | `sync` を回す（一覧ブロックを作り直す） |
| `G006` | 依存の循環 | どちらかを共通の下位ノードに切り出す |
| `G007` | 層の逆流 | 依存の向きを反転させるか、下位層に概念を移す |
| `G008` | `refines` の種別不一致 | 同じ `type` 同士にする、または `depends_on` にする |
| `G009` | `status` 語彙違反 / stable が draft に依存（警告） | 依存先を固めるか、こちらを `review` に落とす |
| `G010` | `related` が片側だけ（警告） | 相手側にも `related` を書く |
| `G011` | 未確定のまま長期間放置（警告） | 確定させる、削除する、あるいは意図的なら理由を本文に書く |
| `G012` | 参照されすぎ（警告） | 概念が混ざっていないか点検し、必要なら分割する |
| `G013` | 依存先が禁じた言い換えを使用（警告） | 正しい用語に直す、または禁止の範囲が広すぎるので用語表を直す |
| `G014` | テンプレートの必須の節が無い（警告） | 節を足す。書くことが無いなら「なし」と書く |
| `G015` | 依存先が変わったのに追従していない（警告） | 依存先の変更を見て、追従が要るか確かめる。要らなければそのままでよい |
| `G016` | `implemented_by` の指し先が存在しない | パスを直すか、宣言を外す |
| `G017` | 文書と実装のどちらか片方だけが変わった（警告） | もう片方を見て、追従が要るか確かめる |
| `G018` | README の図が GitHub の描画上限に近い / 超えている | `graph.mk` に `README_GRAPH_ARGS = --aggregate` を置く |
| `G019` | Markdown の表が途中で切れている | 挟まっている段落や空行を表の外へ出す |
| `G020` | 取り下げた決定を断りなく引いている（警告。**README も見る**） | 生きている決定に差し替える（経緯は書き足さない） |
| `G021` | 自動生成ブロックより後ろに本文がある | 本文をブロックの前へ移す |

`G001`〜`G008` と `G016` は構造の誤りで、直さなければ壊れている。
`G009`〜`G015` と `G017`・`G020` は**健全性の警告**で、承知のうえで放置してもよい。
`G018` は**近づいていれば警告、超えていればエラー。** 超えた時点で README の図は
GitHub 上で描画されておらず、壊れているため。
**`G019` と `G021` はエラー。** 表が切れていればその行は GitHub 上でただの文字列
として出ているし、自動ブロックの下に回った本文は読む人に届いていない。
どちらも**「承知のうえで放置してよい」場合が無い**ので警告にしていない。
`check` は既定で警告を失敗にしない（`--strict` を付けたときだけ失敗する）。

**CI では main への push だけ `--strict` を使う。** 開発中のブランチと PR では
警告を出すだけにして、書いている途中で止めない。警告は
「直すべきだが、今すぐ壊れてはいない」ものなので、**入る前に直せば足りる。**

### G011: 放置された未確定ノード

`draft` / `review` のまま `STALE_AFTER_DAYS`（既定 90 日）を超えて更新がないと警告する。

判定は「いつ `draft` になったか」ではなく「**最後に触られたのはいつか**」。
書きかけでも手が入り続けているなら問題ではなく、止まっていることが問題だから。

日付は git の履歴から取る。次の場合は**黙って検査を飛ばす**（誤検知より無検知を選ぶ）。

- git が無い、リポジトリではない
- 浅いクローン（全ファイルが同じ日付になり判定にならない）
- そのファイルがまだコミットされていない

CI で有効にするには `actions/checkout` に `fetch-depth: 0` が要る。
履歴を見せたくないときは `check --no-history` で明示的に飛ばせる。

### G012: 参照されすぎているノード

`depends_on` で `MAX_INCOMING_DEPENDENCIES`（既定 8）を超えて参照されると警告する。

参照が集まるノードは複数の概念が混ざっていることが多い。変更したときの
影響範囲が広く、追従の確認コストが跳ね上がる。分割の合図として使う。

ただし**語彙の中心になるノードは、参照が多くて当然**でもある。
点検した結果「これでよい」と判断したなら、しきい値を上げるか警告のまま放置してよい。

### G013: 依存先が禁じた言い換え

ドメインノードの「用語」表に書いた**使ってはいけない言い換え**が、そのノードに
`depends_on` / `refines` で（間接にでも）繋がっている文書で使われていると警告する。

| 用語 | 意味 | 使ってはいけない言い換え |
| --- | --- | --- |
| 認定 | 未認定ロールを外し、認定ロールを付ける一連の操作 | 承認、昇格（第三者が判断する語感になる） |

この表を書いた時点で検査が効き始める。**表を書かなければ何も起きない。**

繋がりは間接も辿る。契約はユースケース経由でドメインに繋がるので、直接の
`depends_on` だけを見ると「契約が語彙を破っている」場合を丸ごと見落とす。

末尾の丸括弧はセル全体にかかる注記として扱い、警告に添える。禁止の理由でも、
使ってよい条件（「入力欄の呼称としてのみ使う」など）でもよい。

**この検査は語の意味までは分からない。** 次のような当たりも出る。

- 別の概念について同じ語を使っている（大会の「終了」と対戦の「終了」）
- 否定するために持ち出している（「第三者の承認は挟まない」）

だから警告に留めてある。出たら 3 通りの直し方がある。

1. 本文の語を正しい用語に直す
2. **用語表の側を直す。** 意図して使っている場面があるなら、その禁止は範囲が
   広すぎる。条件つきなら注記に書き、無条件に禁じられないなら一覧から外して
   「意味」の欄で違いを説明する
3. **足りない用語を足す。** 指しているものに名前が無いために、禁止語へ
   流れていることがある。その概念をドメインノードに定義する

`--strict` を使うなら 1〜3 のどれかで消しきる必要がある。
消さずに残すなら `--strict` を使わない。

#### 上位層は検査されない

`10-architecture` は `20-domain` に依存できない（層の逆流になる）。辿る辺が無いので、
**アーキテクチャ文書はドメインの用語表で検査されない。** ADR とメタも同様。

**用語としては従うこと。** 同じものを指しているなら同じ語で書く。
ただし**これは規約であって、機械では確かめられない。**

到達範囲を広げる案を実プロジェクト 3 件で測ったが、どれも採れなかった。

| 案 | 増える件数 | そのうち妥当 |
| --- | --- | --- |
| 依存の逆向きも辿る | +2 | 1 件。**どの文書が捕まるかが偶然で決まる** |
| `related` も辿る | +0 | — |
| グラフ全体を見る | +30 | 2 件 |

「グラフ全体」が破綻するのは、目次や規約文書が「## 追加するとき」「層ルール」の
ような一般語を使うため。**ドメインの語彙とは無関係に正しい文章が大量に当たる。**
逆向きは、たまたまドメインが依存しているアーキテクチャ文書だけが検査される。
検査される・されないの境目に意味が無い。

見出しと列名は `schema.py` の `TERM_SECTION_HEADING` / `TERM_COLUMN` /
`TERM_FORBIDDEN_COLUMN` で差し替えられる。1 文字の語は本文のどこにでも現れるため
対象外（`TERM_MIN_LENGTH`）。

#### 禁止語を足すときは、先に本文を検索する

**実際に使われている語を後から禁じると、正しい文章が大量に当たる。**
用語表に 1 行足す前に、その語がすでにどう使われているかを見る。

```bash
grep -rn "禁じたい語" docs/
```

自分の文書が使っているなら、それは禁止語ではなく**別の意味で正しく使っている語**
かもしれない。「不戦勝」を禁じようとして、そのノード自身が別の意味で使っていた、
という取り違えが実際に起きている。

#### 依存が無い者どうしの衝突は見つからない

**同じ語を別々の概念に使っていても、依存関係が無ければ検出されない。**

実例として、総当たり形式とトーナメント形式が「不戦勝」を別の意味で使っていた
（片方は「相手がいない」、もう片方は「来なかった」）。**この 2 つは兄弟で、
互いに依存していない**ので、どちらの用語表を書いても相手に届かない。

**兄弟ノードの用語は目で見るしかない。** 同じ親を `refines` している
ノードどうしは、特に語が重なりやすい。

#### 兄弟の禁止語は、共通の依存元で衝突する

前節の裏返しが起きる。**兄弟どうしには届かないが、両方に依存しているノードには
両方の用語表が届く。** そこでは片方の正式な用語が、もう片方の禁止語になっている。

先ほどの 2 つの形式で実際に起きた。総当たり形式の用語表に
「棄権の言い換えとして『不戦勝』を禁じる」と書いたところ、
**対戦表を生成するユースケースが警告を受けた。** そのユースケースは両方の形式を
扱うので両方に `depends_on` していて、そこで「不戦勝」を使うのは正しい。
トーナメント形式の正式な用語だからである。

直し方は 2 番（用語表の側を直す）になる。**兄弟が正式に使っている語は
禁止語にできない。** 「意味」の欄で違いを説明するに留める。

言い換えると、**禁止語を足す前に見るべき本文は自分の依存元だけではない。**
兄弟ノードの用語表と、その兄弟に依存しているノードの本文も見る。

```bash
python -m tools.graph render --format json --focus DOM-05 --depth 2
```

**この衝突は、概念が分かれていることの現れでもある。** 同じ語を別の意味で
使う 2 つの形式が両方とも必要なら、それは分割が正しかったということになる。

#### 部分一致であること

語の照合は単純な部分一致で、**長い語の中に短い禁止語が含まれると当たる。**
「参加」を禁じると「参加コード」も当たる。

これは弱点であると同時に、**用語の作り方への警告でもある。** 禁じた語を
含む新しい用語を作れば、その語が持つ曖昧さも引き継いでいる。

### G014: テンプレートの必須の節

`type` ごとに決めた節が本文にあるかを見る（`schema.REQUIRED_SECTIONS`）。

```python
REQUIRED_SECTIONS = {
    "domain": ("定義", "不変条件", "用語"),
    "usecase": ("概要", "事前条件"),
}
```

**中身までは見ない。見出しがあることしか確かめられない。**
だから「なし」と書いてあれば通る。それでよい。
**書く場所を用意させることと、書かないと決めたことを明示させる**のがこのルールの役目で、
何を書くかは人が決める。

#### 雛形の全節を必須にしない

**必須にするのは「これが無いと文書として成立しない」節だけ。**
雛形には「書くことがあれば書く」節も含まれている。

実データで測った。**雛形の全節を必須にすると、141 ノード中 50 件（35%）が落ちた。**
その多くは意図的な省略である。

- ログを扱うドメインノードに「ライフサイクル」が無いのは、**寿命の状態遷移が無いから**
- 大会のノードに「ライフサイクル」が無いのは、**「状態」という節に書いてあるから**

これは規約の「**層を無理に埋めない**」（3 節）と同じ話で、
節についても**埋めるために中身の無い見出しを作らせてはいけない。**

既定値は、既存ノードのほぼ全てが実際に持っている節から決めてある。
**プロジェクトの語彙に合わせて書き換えてよい。**

#### refines の子には親の節を求めない

`refines` を持つノードは 1 つの文書を分けたもので、**親が持つ節を繰り返さない。**
総当たり形式のノードに「定義」「属性」が無いのは、親の大会ノードが持っているためである。

`REQUIRED_SECTIONS_REFINED` に `type` があれば、そちらが使われる。

#### 契約層は検査していない

**契約には形が複数ある。** HTTP の API、チャットの操作、ファイル形式。
実データを見ると、**90% 以上のノードが持つ節が 1 つも無かった**（最頻の
「受け口の一覧」で 13 件中 9 件）。

共通の形が無いものに共通の必須節は置けないので、`contract` は空にしてある。
**形が固まってから足す。**

### G015: 依存先が変わったのに追従していない

**このルールだけはグラフの状態ではなく、変更の状態を見る。**
窓の中で依存先（`depends_on` / `refines`）が動き、依存元が動いていないノードを挙げる。

窓は既定で**未コミットの変更**。書いている途中に効く。

```bash
python -m tools.graph check
```

`--since` で窓を広げる。その参照との分岐点から `HEAD` まで（作業ツリーも含む）。

```bash
python -m tools.graph check --since origin/main
```

`--no-history` を付けるか、git リポジトリでなければ**何も出ない。**

#### なぜ「依存先のほうが新しい」で見ないのか

git の最終更新日を比べて「依存先のほうが自分より新しい」を出せばよさそうに見える。
実データで測ると、**4 リポジトリ 212 ノード中 47 件（22%）が恒常的に引っかかった。**

中心的なノードは頻繁に触られるので、それに依存している側は常に「古い」。
**これは腐敗ではなく定常状態である。**しかも一度出た警告は、依存元を
書き換えるまで消えない。**見て「変えなくてよい」と判断しても消えない。**

見たいのは腐敗ではなく**取りこぼし**、つまり
「いま依存先を書き換えたのに、依存している側を見ていない」である。
これは変更の窓の中でしか意味を持たない。**窓を閉じれば（コミットすれば）消える**ので、
消えない警告が積み上がらない。

同じ実データで、コミット 1 件あたりの件数は中央値 0〜7、最大 32 だった。

#### 自動ブロックだけの変化は数えない

`graph:auto` の中身は `sync` が生成しているので、**依存元が追従する余地が無い。**
そこだけが変わったファイルは、変更として数えない。
数えると `sync` を回すたびに警告が出る。

#### 直接の依存だけを見る

推移的には辿らない。DOM-01 が変わったとき、DOM-01 を `depends_on` している
UC-01 は挙がるが、**UC-01 にしか依存していないノードは挙がらない。**

辿ると 1 回の変更でグラフの大半が挙がり、一覧としての意味が無くなる。
影響が遠くまで及ぶと考えるなら、`render --focus <ID> --depth 2` で自分で辿る。

#### 追従が要るとは限らない

**依存先の変更が依存元に関係しないことは多い。**
このルールは「見たか」を確かめるもので、「直せ」ではない。
一覧を見て「変えなくてよい」と判断したなら、そのまま進めてよい。

規約の散文に「影響範囲を確かめる」と書いても、**確かめたかどうかは残らない。**
変更した瞬間に一覧を突きつけるところまでが、機械にできる仕事である。

### G016 / G017: 実装との対応

**文書と実装を同じリポジトリに置く場合だけ使う。**
ノードのフロントマターに、その文書が規定している実装を書ける。

```yaml
id: DOM-07
type: domain
title: チーム
implemented_by:
  - tournament/teams.py
```

**書かなければ何も起きない。** 文書だけのリポジトリでは 1 件も宣言されないので、
`G016` も `G017` も発火しない。用語表の「使ってはいけない言い換え」と同じ扱いである。

#### これはエッジではない

**ソースはノードではない。** 層（`G007`）にも循環（`G006`）にも到達性（`G005`）にも
関係しない、グラフの外への**指し先**である。

エッジにすると、実装ファイルを目次に登録しろと言われ、層の向きを問われ、
`refines` を持てるのかと聞かれることになる。**どれも答えが無い。**

#### G016: 指し先が存在するか（エラー）

本文の `[[ID]]` に対する `G004` と同じ役割である。
**指し先が消えても文書はそのまま読めてしまう**ので、機械が確かめないと静かに腐る。

指せるのは**同じリポジトリの中のパスだけ。** ファイルでもディレクトリでもよい。
別リポジトリの実装は指せない。

#### G017: 片方だけが変わっていないか（警告）

**`G015` を文書と実装の境界にまたがらせたもの。** 見ているのは同じく変更の窓の中だけで、
両方が同じ窓に入っていれば何も言わない。

**どちらの向きも出す。**

| 動いたもの | 出るもの |
| --- | --- |
| 実装だけ | 「実装が変わりました。文書の追従が要るか確かめてください」 |
| 文書だけ | 「実装は動いていません。実装の追従が要るか確かめてください」 |
| 両方 | 何も出ない |

**どちらが正しいかは機械には分からない。** 実装の内部を整理しただけなら文書は動かないし、
先に文書を決めてから実装するなら文書だけが動く。
`G015` と同じく「見たか」を確かめるルールで、「直せ」ではない。

#### 粒度は実データで決める

4 リポジトリで測ったところ、**実装のコミットの 95%（tournament）と 100%（medieval-idle）が
文書の id をコミットメッセージで参照していた**（97 種・17 種、いずれも全部実在した）。
**繋がりは既にあり、確かめる手段だけが無かった。**

対応の粒度は層によって違う。

| 層 | 実装との対応 |
| --- | --- |
| ドメイン | **ほぼ 1 対 1**（チーム → `teams.py`、エントリー → `entries.py`） |
| 契約 | **多対少。** 画面を作るモジュールが全契約に共通で現れる |
| アーキテクチャ / ADR | 対応するファイルが無いことが多い。**宣言しなくてよい** |

### G018: README の図が GitHub の描画上限に近い

GitHub は Mermaid の図を**エッジ 500 本まで**しか描かない。超えると図が丸ごと消え、
`Edge limit exceeded. 500 edges found, but the limit is 500.` という短い文言だけが残る。

**上限は図の中からは変えられない。** `mermaid.initialize` の `maxEdges` は GitHub 側の
設定で、図に書いても効かない（安全のため無視される）。自前でホストする HTML なら
引き上げられるので、**全体図は Pages 側に置き、README には間引いた図を置く**のが基本。

数えているのは**グラフではなく README に実際に入っている図**である。
`--aggregate` や `--focus` で間引いていれば、その結果を数える。GitHub が描こうと
するのもその図そのものだから。

| 状態 | 深刻度 |
| --- | --- |
| `MERMAID_WARN_EDGES`（既定 450）未満 | 何も言わない |
| 450 〜 499 | 警告 |
| **500 以上** | **エラー**（既に描画されていない） |

**500 ちょうどで既に落ちる。** GitHub が返す文言が
`500 edges found, but the limit is 500` で、その時点で図は消えている。

#### 直し方

`render --aggregate` で**型ごとに 1 つの箱へまとめる。** ノードが何件あっても
箱は型の数だけ、エッジは「型 × 種別 × 型」の組み合わせだけになるので、
**ノードが増えても図は大きくならない。**

リポジトリごとに選ぶ。`graph.mk` に次の 1 行を置く（テンプレートは配らないので競合しない）。

```make
README_GRAPH_ARGS = --aggregate
```

そのうえで図を作り直す。

```bash
make readme
```

**小さいリポジトリで使わないこと。** 集約は個別のノードを消す。上限に対して
余裕があるうちは、縮む余地が無いまま情報だけ失う。

### G019: Markdown の表が途中で切れている

Markdown の表は**ヘッダ行と区切り行（`| --- |`）で始まり、空行か本文で終わる。**
途中に段落や空行が入ると、**そこから先の行は表ではなくただの文字列として描画される。**

```markdown
| 用語 | 意味 |
| --- | --- |
| 形式 | 対戦の組み方 |

ここに段落を書いてしまった。
| 進行中 | 結果を入れている状態 |   ← この行はもう表ではない
```

**`G018` と同じ形の問題である。** グラフの検査は全部通るのに、
GitHub 上の見た目だけが壊れる。実際に 2 件見つかった。

| どこ | 何が起きたか |
| --- | --- |
| README のコマンド表 | 案内文を行の間に挿し込み、**以降の 14 行が本文として流れた** |
| ドメインノードの用語表 | 段落 3 つを挟んで **1 行が取り残された** |

**どちらも `check` は通っていた。** `G013` の用語表パーサは行ベースなので、
取り残された行すら拾えている。**機械は困らず、読む人だけが困る。**

#### 判定

`|` で始まる行のうち、次のどちらでもないものを切り離された行とみなす。

- 直前の行も `|` で始まる（＝表の続き）
- 次の行が区切り行（＝正しい表の先頭）

**コードブロックの中は見ない。** この規約自身が上の悪い例を載せているので、
見ると自分の文書で落ちる。

段落を挟んだ**2 つの表は正しい**（2 つ目にヘッダと区切りがあるため）。

#### 直し方

挟まっている段落や空行を、表の外へ出す。**表は 1 つに繋げる。**
補足を行ごとに書きたいなら、セルの中に入れるか、表の後にまとめて書く。

### G020: 取り下げた決定を現在の根拠として引いている

本文が `deprecated` なノードを指していると警告する。

**問題は「参照していること」ではなく「現在の根拠として引いていること」である。**
実データでは、**置き換え先の ADR がすでに決まっているのに古いほうを指したまま**、
という形がユースケース層と契約層に集中して残っていた。

```markdown
報告期限は締めである（[[ADR-0008]]）。   ← ADR-0008 は取り下げ済み
```

**歴史として引くのは正当なので、エラーにはできない。**
「以前は X と書いていた（`ADR-0008`）」は正しい使い方である。
`G009`〜`G015` と同じ警告にして、承知のうえで放置できる形にした。

**`G009` とは重ならない。** あちらは `stable` なノードの `depends_on` だけを見る。
こちらは `status` を問わず**本文のリンク**を見るので、実データの残りは
ほとんどこちらでしか出ない。

#### 判定

本文リンク（`[[ID]]` と `[題](./xxx.md)` の両方）の指し先が `deprecated` なら警告する。
ただし次は黙る。

| 黙る条件 | なぜ |
| --- | --- |
| **確定した記録**（既定では `stable` な ADR） | **確定した ADR は書き換えない。直せないものを鳴らさない** |
| 自分が連鎖上の置き換え先である指し先 | **置き換えた側は指さないほうがおかしい** |
| `index` ノード | 一覧は取り下げたものも並べる。それが仕事である |
| 自分も `deprecated` | 歴史が歴史を引いている |
| **同じ段落の中で置き換え先も指している** | その場で断っている |

#### README も見る

**README はノードではないが、決定を引く。** `graph.nodes` だけを回っていたころは
届かず、**README だけが古い世界を説明し続けることができた。**

7 リポジトリで実測したところ、**3 つの README** が取り下げ済みの ADR を
現在の根拠として引いていた。1 つは**移った先の事実を古いまま述べていた**
（「3 つの Bot を同居」。置き換えた決定の題は「台数を問わない」）。
**README はノードより読まれるのに、検査はノードより薄かった。**

判定はノードと同じで、違うのは 2 つだけ。

| | ノード | README |
| --- | --- | --- |
| 相対リンクの基準 | 自分のディレクトリ | **リポジトリの根** |
| 「自分が置き換えた側」の免除 | 効く | **効かない**（ノードではないので id が無い） |

**見るのは `README.md` だけ。** `CONTRIBUTING.md` と `CLAUDE.md` は実測で 0 件で、
`CLAUDE.md` は派生が共有しているため、**テンプレート側の 1 件が全派生で鳴る。**

**自動生成の図は数えない。** コードブロックの中にあり、判定の前に落ちる。

#### 確定した記録は対象にしない

**ADR は確定したら書き換えない。** 決定を変えるときは本文を直さず、
新しい ADR を起こす。**古い ADR に要るのは後継へのリンクだけ**で、
本文の維持は要らない。

したがって、確定した ADR に「直してください」と言う指摘は**原理的に解消できない。**
直すこと自体が原則に反する。鳴らし続けても `--strict` を塞ぐだけである。

**確定前（`draft` / `review`）は対象に残す。** まだ決めている途中なので直してよい。
境目は「ADR かどうか」ではなく「**確定した記録かどうか**」である。

種別は `schema.py` の `IMMUTABLE_RECORD_TYPES` にある。既定は `adr` だけ。

**残るのは実質、現在の設計を述べる層**（`10-architecture`〜`40-contracts`）である。
そこは「いまどうなっているか」を書く場所なので、古い決定を指していたら
**生きている決定に差し替える。**

**置き換え先は連鎖を辿る。** `ADR-0004` → `ADR-0006` → `ADR-0007` と置き換わったとき、
`ADR-0004` の置き換え先は `ADR-0006` と `ADR-0007` の両方である。
**現在の決定（連鎖の先端）を指すのは、直接の置き換え先を指すより正しい。**
片方しか認めないと、「`ADR-0004` の時点」と「現在（`ADR-0007`）」を並べた表が鳴る。

同じ理由で、**連鎖の先にいる側は遡って引いてよい。** `ADR-0007` が 2 つ前の
`ADR-0004` を引くのは「あちらはこう決めていた」と書いているだけで、
直接の置き換え先を引くのと変わらない。

最後の 1 つが効きどころで、**段落に絞ることに意味がある。**
7 リポジトリで実測して決めた。

| 案 | 鳴る引用箇所 |
| --- | --- |
| 段落の中で指していれば黙る | 64 |
| 文書のどこかで指していれば黙る | 取りこぼしが出た |

**「文書のどこかにあれば足りる」にはしない。** 長い文書では別の話題で
置き換え先に触れているだけで黙ってしまい、本物を取りこぼす。

#### 直し方

**生きている決定に差し替える。**

```markdown
報告期限は締めではない（[[ADR-0014]]）。
```

**経緯を書き足さない。** 「かつては `ADR-0008` に従うと書いていた」は
この層に要らない。文書自身の履歴は git にあり、決定の経緯は ADR 層にある。
**正しく直すと、取り下げた ADR への参照ごと消えて短くなる。**

差し替えるには「どこまでが生きているか」が要る。**それは置き換えた側の ADR の
「決定」にしか書かれていない。** `adr.md` 雛形の「決定」の案内が、
置き換えるときに引き継ぐ範囲を書かせているのはこのためである。
書いてあれば、この警告は相手を 1 本読むだけで直せる。

歴史として引いていることが本当に要るなら、**そのまま放置してよい。**

### G021: 自動生成ブロックより後ろに本文がある

`sync` が書く自動生成ブロックの終わりより後ろに、空白以外が残っていたらエラーにする。

自動ブロックは「関連ドキュメント（自動生成 / 手で編集しない）」という**文書の締め**
である。**その下に本文が続くとは読む人は思わない。** しかも CLAUDE.md が
「この塊を手で編集するな」と書いているので、**下の本文を直したい人は
「触るな」と書かれた塊を越えて行くことになる。**

**`sync` は自分では直せない。** ブロックが既にあれば**その場で入れ替える**だけで、
後ろに回った本文は動かさない。だから一度こうなると、黙って残り続ける。

**実際にこの文書（`META-01`）で 84 行が落ちていた。** 5 節のルール一覧から
`G015`〜`G019` が切り離され、そのうち `G018` と `G019` は自動ブロックより
下にあった。**共有ファイルなので 7 リポジトリすべてが同じ状態だった。**
1.14.2 で直してある。

#### 判定

目印は `graph:auto:end` **だけ**を見る。

**目次の `graph:children:end` は見ない。** 一覧の後ろに「使い方」を書くのが
目次の正しい形なので、そこを見ると目次が丸ごと落ちる。

ブロックが 2 つある文書は既に壊れているが、**最後の 1 つ**を基準にする。
間に挟まった本文まで数えると、直す場所が分からない指摘になる。

`sync` を一度も回していない文書（ブロックが無い）には**何も言わない。**

#### 直し方

**本文をブロックの前へ移す。** ブロックは文書の最後に置く。

並べ替えたあとは、行の多重集合が元と一致することを確かめると安全である
（本文を書き換えずに動かしただけ、と言い切れる）。

## 6. 運用サイクル

1. `python -m tools.graph new --type usecase --id UC-02 --title "..."` でノードを起こす
2. 本文とフロントマターの `depends_on` を書く
3. `python -m tools.graph check` が通るまで直す
4. `python -m tools.graph sync` で各文書末尾の関連リンクを再生成する
5. コミット（CI でも 3 と 4 を検証する）

まとめて起こすときは、1 行 1 ノードのファイルを渡す。

```bash
python -m tools.graph new --from docs/00-meta/new-nodes.txt
```

```
# type | id | title | slug | status | template
usecase | UC-02 | 予約をキャンセルする | cancel-booking
contract | CON-02 | キャンセル API | cancel-api | draft | contract-http
```

`slug` 以降は省略できる。1 件失敗しても残りは作られ、失敗した分だけが報告される。

## 7. 雛形

雛形は `00-meta/templates/` にあり、既定では `<type>.md` が使われる。
同じ type に複数の書式が要るときは `--template` で選ぶ。

| 雛形 | 用途 |
| --- | --- |
| `contract.md` | 伝送方式に依存しない「境界をまたぐ約束事」。既定 |
