# グラフの規約

設計文書をグラフとして扱うための規約。**すべて `python -m tools.graph check` で機械検証できる**
形にしてある。ルール ID（G0xx）は検証結果に必ず出るので、エラーが出たらここを引く。

## 1. ノード

- 1 つの Markdown ファイル = 1 ノード。
- 先頭に必ずフロントマターを置く。

```yaml
---
id: UC-01              # 必須。型ごとの接頭辞つき
type: usecase          # 必須。node-types.md の語彙
title: 予約を確定する    # 必須。一覧に出る名前
status: draft          # 必須。draft / review / stable / deprecated
tags: [booking]
depends_on:
  - DOM-01
related: []
---
```

フロントマターは YAML のサブセット（スカラー・インラインリスト・ブロックリスト）のみ。
ネストしたマップや複数行文字列は使わない。

## 2. エッジ

エッジは 2 種類の書き方がある。**意味を持つのはフロントマターの側だけ。**

| 書き方 | 例 | 検証対象 |
| --- | --- | --- |
| フロントマター（型つき） | `depends_on: [DOM-01]` | リンク切れ・層・循環・成熟度 |
| 本文の `[[ID]]` / 相対リンク | `[[DOM-01]]` | リンク切れのみ |

### 本文リンクは層と循環の検査を受けない

これは意図的な逃げ道であり、**規約の穴でもある**。本文には、下位層のノードから
上位層のノードへの言及を書けてしまう。

```markdown
<!-- 層 30 のユースケースに、層 40 の契約への言及を書ける（検証は通る） -->
- [ ] 出力したファイルが文字化けしない（[[CON-02]]）
```

同じことをフロントマターの `depends_on` に書けば `G007` で落ちる。使い分けの基準は次のとおり。

- **前提**なら `depends_on` に書く。層の逆流になるなら、それは設計が壊れている合図
- **補足の道案内**なら本文に書く。「詳細はこちら」程度の参照で、消しても文書が成立するもの

本文リンクが増えてきたノードは、`depends_on` に書くべきものが紛れていないか点検する。

### リンクとして数えない場所

次の中にある `[[ID]]` や相対リンクは、リンクとして扱わない。

- コードブロック（``` で囲まれた範囲）とコードスパン（`` ` `` で囲まれた範囲）
- HTML コメント（`<!-- -->`）

規約や雛形に「書き方の例」を載せてもリンク切れにならないようにするため。
逆に言うと、**コメントアウトした参照はグラフに現れない**。

型つきエッジの種類:

| 種類 | 意味 | 制約 |
| --- | --- | --- |
| `refines` | **分割元**のノード。1 つの文書を分けたときだけ使う | 同じ `type` 同士のみ / 循環禁止 |
| `depends_on` | これが成立する前提となるノード | 層の逆流禁止 / 循環禁止 |
| `related` | 依存しないが併読すべきノード | 相互に書くこと（片側だけなら警告） |
| `supersedes` | この決定が置き換える過去の決定 | ADR 同士のみ |
| `decides` | この決定が影響を与えるノード | ADR 起点 |

### `refines` と `depends_on` の使い分け

同じ `type` 同士では両方が書けてしまうので、基準を決めておく。
**迷ったら `depends_on`。** `refines` を使うのは分割したときだけ。

| 問い | はい | いいえ |
| --- | --- | --- |
| その 2 つは、もともと 1 つの文書だったか（1 つに戻せるか） | `refines` | `depends_on` |

```yaml
# ○ 分割: UC-03 が大きくなったので入口ごとに切り出した
# uc-09-...md
id: UC-09
title: ボタン経路で匿名投稿する
refines:
  - UC-03      # 親。共通の事前条件・事後条件は親が持つ

# ✗ 誤用: 匿名メッセージはロールの「一部」ではない。前提であって分割ではない
id: DOM-02
refines:
  - DOM-01     # ここは depends_on が正しい
```

分割するときは、**親に全体の見取り図と共通部分を残す**。親が空になるなら、
それは分割ではなく置き換えなので `refines` は使わず、親のノードを畳む。

## 3. 層の向き

依存は **抽象度の高い側へ向ける**。逆向きは `G007` で落ちる。

```
40-contracts ──depends_on──▶ 30-usecases ──depends_on──▶ 20-domain ──depends_on──▶ 10-architecture
```

ドメインがユースケースを知っている状態は設計の破綻なので、規約ではなく検証で止める。
ADR（`50-adr/`）とメタ文書は横断的なので層ルールの対象外。

## 4. 到達可能性

すべてのノードは [IDX-ROOT](../index.md) から辿れること。新しい文書を作ったら、
その層の `index.md` の一覧ブロックに必ず載せる（`python -m tools.graph new` は自動で載せる）。

## 5. ルール一覧

| コード | 内容 | 直し方 |
| --- | --- | --- |
| `G001` | フロントマターが読めない / 必須キー不足 | `id` `type` `title` `status` を埋める |
| `G002` | `id` の重複 | 片方を採番し直す |
| `G003` | `id` 接頭辞・`type` 語彙・置き場所の不一致 | [META-02](./node-types.md) の表に合わせる |
| `G004` | リンク切れ | 参照先の `id` を直すか、ノードを作る |
| `G005` | ルート目次から到達できない | その層の `index.md` に載せる |
| `G006` | 依存の循環 | どちらかを共通の下位ノードに切り出す |
| `G007` | 層の逆流 | 依存の向きを反転させるか、下位層に概念を移す |
| `G008` | `refines` の種別不一致 | 同じ `type` 同士にする、または `depends_on` にする |
| `G009` | `status` 語彙違反 / stable が draft に依存（警告） | 依存先を固めるか、こちらを `review` に落とす |
| `G010` | `related` が片側だけ（警告） | 相手側にも `related` を書く |
| `G011` | 未確定のまま長期間放置（警告） | 確定させる、削除する、あるいは意図的なら理由を本文に書く |
| `G012` | 参照されすぎ（警告） | 概念が混ざっていないか点検し、必要なら分割する |

`G001`〜`G008` は構造の誤りで、直さなければ壊れている。
`G009`〜`G012` は**健全性の警告**で、承知のうえで放置してもよい。
CI は既定で警告を失敗にしない（`--strict` を付けたときだけ失敗する）。

### G011: 放置された未確定ノード

`draft` / `review` のまま `STALE_AFTER_DAYS`（既定 90 日）を超えて更新がないと警告する。

判定は「いつ `draft` になったか」ではなく「**最後に触られたのはいつか**」。
書きかけでも手が入り続けているなら問題ではなく、止まっていることが問題だから。

日付は git の履歴から取る。次の場合は**黙って検査を飛ばす**（誤検知より無検知を選ぶ）。

- git が無い、リポジトリではない
- 浅いクローン（全ファイルが同じ日付になり判定にならない）
- そのファイルがまだコミットされていない

CI で有効にするには `actions/checkout` に `fetch-depth: 0` が要る。
履歴を見せたくないときは `check --no-history` で明示的に飛ばせる。

### G012: 参照されすぎているノード

`depends_on` で `MAX_INCOMING_DEPENDENCIES`（既定 8）を超えて参照されると警告する。

参照が集まるノードは複数の概念が混ざっていることが多い。変更したときの
影響範囲が広く、追従の確認コストが跳ね上がる。分割の合図として使う。

ただし**語彙の中心になるノードは、参照が多くて当然**でもある。
点検した結果「これでよい」と判断したなら、しきい値を上げるか警告のまま放置してよい。

## 6. 運用サイクル

1. `python -m tools.graph new --type usecase --id UC-02 --title "..."` でノードを起こす
2. 本文とフロントマターの `depends_on` を書く
3. `python -m tools.graph check` が通るまで直す
4. `python -m tools.graph sync` で各文書末尾の関連リンクを再生成する
5. コミット（CI でも 3 と 4 を検証する）

まとめて起こすときは、1 行 1 ノードのファイルを渡す。

```bash
python -m tools.graph new --from docs/00-meta/new-nodes.txt
```

```
# type | id | title | slug | status | template
usecase | UC-02 | 予約をキャンセルする | cancel-booking
contract | CON-02 | キャンセル API | cancel-api | draft | contract-http
```

`slug` 以降は省略できる。1 件失敗しても残りは作られ、失敗した分だけが報告される。

## 7. 雛形

雛形は `00-meta/templates/` にあり、既定では `<type>.md` が使われる。
同じ type に複数の書式が要るときは `--template` で選ぶ。

| 雛形 | 用途 |
| --- | --- |
| `contract.md` | 伝送方式に依存しない「境界をまたぐ約束事」。既定 |
| `contract-http.md` | HTTP の API。エンドポイントとステータスコードを持つ |

```bash
python -m tools.graph new --type contract --template contract-http --id CON-02 --title "..."
```

雛形そのものはグラフに含めない（`EXCLUDE_PREFIXES` で除外している）ため、
`{{ID}}` のような未置換の記述が残っていても検証には出ない。
