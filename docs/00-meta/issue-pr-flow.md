# issueとPRの流れ

見つけたことや決めることをissueにし、変更をPRで出すまでの流れを決める。文書だけのリポジトリでも、文書と実装を同じリポジトリに置くリポジトリでも、同じ流れを使う。

統合型の層（`graph-project-template`）では、開発の流れ（META-05）が、作業の順番の中でこの文書を参照する。

## 1. issueを立てる

問題が見つかったとき、要件が出たとき、今後のTODOができたときは、issueにする。チャットや手元のメモで終わらせない。残らないものは、決める作業の入口にならない。

型は3つあり、`.github/ISSUE_TEMPLATE/`に置いてある。

| 型 | いつ使うか | 閉じるとき |
| --- | --- | --- |
| 要件 | 機能や文書の追加・変更を始める。決めることが書ける | 決めることに答えが出たとき |
| 問題 | 見つかった不具合。現象しか書けない | 原因が分かったとき。直すのはPRの仕事 |
| TODO | いま着手しないが、条件が揃ったらやること | 条件が揃って取りかかり、結論が出たとき |

どの型も、まだ答えが無い問いを持つ。答えが分かっているものは、issueではない。迷ったら、決めることが書けるかで分ける。書けるなら要件、現象しか書けないなら問題、いま決めようが無いならTODOである。

### 決まったことは文書へ移す

**issueを閉じるのは、問いに答えが出て、決まったことを文書へ移したときである。** issueは閉じたら終わるが、文書は残る。

| 決まったこと | 移す先 |
| --- | --- |
| なぜその判断にしたか、却下した案 | ADR |
| 振る舞いと受け入れ条件 | ユースケースの「受け入れ条件」 |
| 概念と言葉 | ドメインノードの「定義」「用語」 |

issueを、作業計画の置き場にしない。受け入れ条件はユースケースが持ち、決定はADRが持っている。issueにも同じものを書くと、2か所を保守することになる。

実装を同じリポジトリに置く場合は、実装の置き場と`implemented_by`の書き方を、統合型の層の文書（META-04）が決めている。

### テンプレート由来のものは上流に出す

派生のリポジトリにissueを立てても、上流のテンプレートには届かない。派生で気づいたテンプレートの欠陥は、上流のリポジトリに直接issueを立てる。issueの作成画面に、上流へのリンクを置いてある（`.github/ISSUE_TEMPLATE/config.yml`）。

| 何の話か | 出し先 |
| --- | --- |
| `tools/graph`と`G0xx`の検査、issueとPRの流れ | 検証ツールの層（`graph-doc-template`） |
| 文書と実装の同居・実装のCI・配置 | 統合型の層（`graph-project-template`） |

どの派生で、何をしていて気づいたかを書く。テンプレートの改善の大半は、配って初めて分かる欠陥から来ていて、それは使っている側にしか見えない。

### Projectへの追加

issueとPRは、GitHub Projectに自動で載せられる。先にProjectに組み込まれたAuto-addを使い、数が足りないときだけ`.github/workflows/add-to-project.yml`を使う。設定の仕方とボードの読み方は、そのファイルの冒頭にある。

## 2. PRを出す

### 1つのPRには、1つの変更だけを入れる

**PRの題を、「〜と〜」「〜・〜」のように並べずに1文で書けるなら、1つの変更である。** 並べないと書けないなら、PRを分ける。その変更に関係するテスト・文書・変更履歴は、同じPRに入れる。どのPRも、マージしたあとに`check`とテストが通る状態を保つ。

分ける理由は、レビューしやすさと、戻しやすさである。2つの変更が1つのPRに入っていると、片方だけを戻したいとき、もう片方まで戻ってしまう。

1つのissueを、複数のPRに分けるのはよい。たとえば、文書の書き直しを、ファイルのまとまりごとに分ける。それぞれのPRが、単独で上の条件を満たしていればよい。

作業の途中で種類の違う変更を見つけたら、別のPRにする。

| 見つけたもの | どうするか |
| --- | --- |
| 書き直しの途中で見つけた、中身の誤り | issueにして、別のPRで直す |
| テンプレートの取り込みで、`merge=ours`のファイルに手で反映するもの | 取り込みのPRとは別のPRにする |
| 識別子の改名やコードの移動のようなリファクタリング | 小さくても、別のPRにする |
| 意味も動きも変えない誤字の修正 | 同じPRに入れてよい。本体の変更と一緒に戻っても困らないものに限る |

同じファイルを触っていて競合しそうでも、それを理由にPRを混ぜない。先のPRをマージしてから、その上にブランチを切る。前のPRのブランチの上に次のPRを積むときは、前のPRをマージしてもブランチをすぐには消さない。消すと、それを向き先にしていた次のPRが閉じられる。

迷ったら小さくする。大きく作ってから分けるより、小さく作ってから足すほうが楽である。

### 粒度とサイズは別のものである

判定するのは粒度（変更の内容が1つか）であって、サイズ（変更行数やファイル数）ではない。内容が1つなら、行数が多くてもそのままでよい。

| 内容が1つで、行数が多くてよい例 | 理由 |
| --- | --- |
| テンプレートの取り込み（マージ） | 中身は、上流ですでに確かめてある |
| 外部のものを、そのまま同梱する | 書いたものではなく、写したものである |
| ファイルの削除 | 読む量が少ない |
| 道具による機械的な変更（一括の置き換えなど） | 確かめるのは、道具の結果が意図どおりかだけである |

ただし、変更行数が400行を超えたら、複数のことが混ざっていないかを確かめる。行数は分ける理由ではなく、混ざっていないかを見直す合図である。

### PRにはノードのidを書く

PRの本文の「対応するノード」の節（PRの雛形にある）に、対応するノードのidを書く。CI（`graph-check.yml`の`refs`）が、題とこの節にあるidが実在するかを確かめる。節の外に書いたidは確かめないので、idの振り方の例のように、ノードを指さないidも書ける。節が無い本文では、全体を確かめる。対応する文書が無い変更（依存の更新、テンプレートの取り込みなど）では、節の中の行の頭に`なし`と書く。箇条書きにして`- なし`と書いてもよい。文の途中の「問題なし」などは数えない。

### ブランチ名とコミットの1行目

コミットの1行目は、次の形にする。括弧のノードのidは、当たるノードがあるときだけ付ける。issueの番号も、あるときだけ付ける。

```text
<種類>(<ノードのid>): <日本語の1文>（#issue）
feat(WLD-13): 武器と取り締まりの決まりを作る（#40）
```

テンプレート本体（`graph-doc-template`）では、squashのコミット、つまりPRの題に版を入れる。版は括弧に入れない。括弧はノードのidに使うので、版も入れると使い方が2つになるからである。

```text
<種類>: <版> <日本語の1文>（#issue）
fix: 1.36.14 サンプルを配るテンプレートではreset-samplesを回さない、と手順に書く（#117）
```

派生はマージコミットで本体のコミットを取り込むので、本体のコミットもこの形に合わせる。本体が合っていないと、派生の検査で本体のコミットを外す仕組みが別に要る。

ブランチ名は、`<種類>/<issueの番号>-<内容>`の形にする。内容は英小文字とハイフンで書き、英小文字で始めれば数字も使える。issueが無いときは番号を省く。テンプレートの取り込みは、`chore/template-<版>`にする。版は、`python -m tools.graph upgrade --label`が出すものを使う。遅れている層の版を下の層から並べ、上の層には`project-`のような名前が付く。

```text
feat/121-branch-commit-rules
chore/template-1.37.0
chore/template-project-0.14.0
chore/template-1.38.0-project-0.14.0
```

種類は、Conventional Commitsの次の7つを使う。ブランチ名とコミットで同じ一覧を使うので、ブランチ名からも変更の意図が分かる。標準の語なので、commitlintのような道具や、ほかの人にもそのまま通じる。

| 種類 | 使う変更 |
| --- | --- |
| `feat` | 機能や文書の追加 |
| `fix` | 不具合や誤りの修正 |
| `docs` | 説明の文書だけの変更 |
| `refactor` | 意味も動きも変えない書き換え |
| `test` | テストだけの変更 |
| `ci` | CIの設定の変更 |
| `chore` | 依存の更新や取り込みなど、上のどれにも当たらないもの |

派生で種類を足すときは、リポジトリの根の`graph.toml`に`[commit]`の表を書く。たとえば、連載小説の本文の話を`feat`に混ぜると、設定の追加と見分けが付かない。そうした派生は、本文の話に専用の種類を使う。`graph.toml`が無いリポジトリでは、上の7つだけを使う。

```toml
[commit]
extra_types = ["episode"]
```

ノードのidは、ブランチ名とコミットの必須にしない。文書のリポジトリでは、取り込みや本文の話のように、ノードに当たらない作業が多いからである。文書だけのリポジトリで、これまでのコミットにidが付いていた割合は0〜23%だった。

CI（`graph-check.yml`の`names`）が、PRのブランチ名、PRの題、PRに含まれるマージ以外のコミットの1行目を確かめる。目で見るだけでは、決まりを書いても揃わない。ただし、書き手が選べない次の2つは確かめない。

| 確かめないもの | 理由 |
| --- | --- |
| `claude/`で始まるブランチ名 | Claudeのクラウドのセッションが、自動で付ける |
| `chore/template-<版>`のPRに入るコミット | 決まりより前に書かれた上流のコミットが入る。PRの題とブランチ名は確かめる |

### コミットには、自分の変更だけを入れる

同じ作業ツリーを、別のセッションや別の人が触っていることがある。コミットに足すファイルは、`git add -A`でまとめず、自分が変えたものを名指しする。

## 機械で強制できないもの

次のものは、機械では見ていない。目で見るしかない。

| 見ていないもの | 理由 |
| --- | --- |
| PRの粒度 | 題を並べずに書けるかは、読まないと分からない |
| issueを閉じる前に、文書へ移したか | issueと文書の対応は、記録されていない |
| コミットの1行目が日本語の1文か、種類が変更に合っているか | 読まないと分からない |

この決まりは、Googleのコードレビューの指針（[Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)）、[Pull Requestの粒度について考える](https://zenn.dev/iwamasa/scraps/bff1b472f36307)、[Findyの爆速開発を支えるPull requestの粒度](https://tech.findy.co.jp/entry/2024/10/04/070000)を参考にした。
