# ノード種別と層

この表の実体は、`tools/graph/schema.py`の`NODE_TYPES`である。**語彙を変えるときは、両方を直す。**

| `type` | 接頭辞 | 置き場所 | 層 | 何を書くか |
| --- | --- | --- | --- | --- |
| `index` | `IDX-` | 各ディレクトリ | なし | その層の目次。子ノードの一覧 |
| `meta` | `META-` | `00-meta/` | なし | 規約・語彙。プロダクトの中身は書かない |
| `architecture` | `ARCH-` | `10-architecture/` | 10 | 構成要素と責務、技術選定の前提 |
| `domain` | `DOM-` | `20-domain/` | 20 | 概念・不変条件・用語。UIもAPIも出さない |
| `usecase` | `UC-` | `30-usecases/` | 30 | 誰が何をして、何が起きるか。事前条件と事後条件 |
| `contract` | `CON-` | `40-contracts/` | 40 | 独立に変わりうる相手との取り決め。API・UIの操作・ファイル形式・設定・配置の前提 |
| `adr` | `ADR-` | `50-adr/` | 横断 | 決定・背景・却下した案・影響 |

## 層の数字の意味

数字は抽象度を表し、実行の順番ではない。数字が小さいほど変わりにくく、ほかのノードから依存される側になる。

`depends_on`は、同じか小さい数字の層にしか向けられない（`G007`）。ADRとメタ文書は複数の層にまたがるので、層のルールの対象外である。

## 採番

`ARCH`・`DOM`・`UC`・`CON`は、2桁のゼロ埋めで振る（`UC-01`）。50を超えそうなら3桁に切り替える。**切り替えるときは、既存のidも`rename`で振り直す。** 並びはidの文字列順なので、桁が混ざると`UC-100`が`UC-99`より前に来て、目次の一覧の順番が乱れる。99まで待たずに50で切り替えるのは、振り直す件数が少ないうちに済ませるためである。

`ADR`は、4桁のゼロ埋めで振る（`ADR-0001`）。欠番を作らず、取り消すときは`deprecated`と`supersedes`を使う。

一度振ったidは再利用しない。削除したノードのidは、永久に欠番になる。

## 契約か、アーキテクチャか

`40-contracts`を「外部との約束」と説明すると、どこからが外部かで迷う。自分たちで書いた2つの部品の間の取り決めは契約なのか、構造の話なのか、という迷いである。

判定は、次の1つでよい。

> **片方だけが古いまま動きうるか。**

| はい | いいえ |
| --- | --- |
| 契約（`40-contracts`） | 契約ではない。方針なら`10-architecture`、それ以外は実装の詳細 |

契約が要るのは、両者がずれる可能性があるからである。いつも一緒に変わるものはずれようがないので、取り決めとして固定する意味が薄い。「外部かどうか」ではなく、「別々に変われるかどうか」で見る。

| 対象 | 片方だけ古くなるか | 置き場所 |
| --- | --- | --- |
| HTTPのAPIと呼び出し側 | なる（別々にデプロイされる） | 契約 |
| DBのスキーマとアプリ | なる（マイグレーションは別に走る） | 契約 |
| 保存済みのファイルの形式 | なる（過去のファイルが残り続ける） | 契約 |
| 設定ファイルのキーと実装 | なる（設定は版管理の外にある） | 契約 |
| 配置パスと起動定義 | なる（別々に転送・更新できる） | 契約 |
| 同じコミットで一緒に出る2つの関数 | ならない | 契約ではない |

### 同じ題材が両方に出るのは正常

`10-architecture`と`40-contracts`は、同じものの別の側面を書くことがある。

| 層 | 書くこと | 例 |
| --- | --- | --- |
| architecture | どう分けるか、どこに置くか、なぜその構成か | 「設定は各ディレクトリの`.env`に置く」 |
| contract | 具体的に何が一致していなければならないか | 「キー名とその意味。欠けたときの振る舞い」 |

方針を決めるのがarchitecture、ずれてはいけない点を固定するのがcontractである。重複しているように見えたら、contractのほうに「破ったときに何が起きるか」が書けているかを確かめる。書けないなら、それは契約ではない。

## ノードを分割するとき

1つのノードが大きくなりすぎたら、分割する。目安は、読む人が一度に必要としない情報が、1つのノードに一緒に入っているときである。分割した子には新しいidを振り、親を`refines`で指す。

```
UC-03 匿名でメッセージを投稿する        ← 親。アクター・事前条件・事後条件など共通部分
 ├── UC-09 ボタン経路で匿名投稿する      refines: [UC-03]
 └── UC-10 コマンド経路で匿名投稿する    refines: [UC-03]
```

分割するときは、次のことを守る。

| 守ること | 理由・補足 |
| --- | --- |
| 親を残す | 親には全体の見取り図と共通部分を書く。親が空になるなら分割ではないので、`refines`を使わず、親のノードごとなくす |
| 子のidは新しく振る | 親のidに枝番（`UC-03a`）を付けない。付けると採番の規約から外れる |
| 子も目次に載せる | 載せないと`G005`で落ちる |
| 前提は`refines`で表さない | 別の概念に依存しているだけなら`depends_on`を使う。判断の基準は[META-01](./graph-rules.md)の「`refines`と`depends_on`の使い分け」にある |

`refines`は、同じ`type`同士に限られる（`G008`）。層をまたぐ分割は、分割ではなく概念の切り出しなので、`depends_on`で表す。

## statusの意味

| status | 意味 | 依存してよいか |
| --- | --- | --- |
| `draft` | 書きかけ。中身が崩れてもよい | 参照はできる。`stable`からの依存は警告 |
| `review` | レビュー中。大枠は固まった | 可 |
| `stable` | 合意済み。変更はADRを経由する | 可 |
| `deprecated` | 置き換え済み。`supersedes`の対象 | 新しい依存は作らない |

## ファイル名

ファイル名は`{id を小文字にしたもの}-{英数字スラッグ}.md`の形にする。

```
docs/30-usecases/uc-01-sample-confirm-booking.md
docs/50-adr/adr-0001-graph-driven-docs.md
```

日本語の題からスラッグを作れないときは、`--slug`で明示する。省略すると、`dom-02.md`のようにidだけのファイル名になる。

```bash
python -m tools.graph new --type usecase --id UC-02 --title "予約をキャンセルする" --slug cancel-booking
```

## 雛形

既定では、`00-meta/templates/<type>.md`が使われる。`contract`と`usecase`には、別の種類の雛形もある。

| type | 既定の雛形 | 別の雛形 |
| --- | --- | --- |
| `contract` | `contract.md`（伝送方式に依存しない） | `contract-http.md`（HTTP用）／`contract-interaction.md`（チャットの操作） |
| `usecase` | `usecase.md`（システムの振る舞い） | `usecase-runbook.md`（人間が実行する手順） |
| その他 | `<type>.md` | なし |

```bash
python -m tools.graph new --type contract --template contract-http --id CON-02 --title "..."
```

既定の雛形を汎用にしてあるのは、この層の抽象が「境界をまたぐ約束事」であって、HTTPに限らないからである。UIの操作・メッセージキュー・ファイル形式も、この層に置ける。

### `usecase-runbook`を使うとき

実行者が人間で、順序のある手順（配置、更新、障害対応、移行など）を書くときに使う。

既定の雛形は「システムが〜する」ことを前提にしているので、手順書には「代替フロー」「例外フロー」「事後条件」「受け入れ条件」が当てはまらない。手順書の分岐はフローの分岐ではなく、症状ごとの対処になる。事後条件をドメインの用語で書こうとしても、その語彙が無いことが多い。

`usecase-runbook`は、代わりに「手順」「順序の制約」「つまずきやすい点」「完了の確認」「切り戻し」「未確認」を持つ。手順の中の順序はグラフに乗らないので、本文の「順序の制約」に書く（[META-01](./graph-rules.md)の「順序はグラフに乗らない」）。

### 「切り戻し」を空欄にしない

**「戻せない」は最も重要な答え**で、着手する前に知っておく必要がある。実際に書いてみると、戻せない手順は珍しくない。発行し直したトークンは元に戻らないし、削除したインスタンスは復元できない。どこを過ぎたら戻せなくなるかまで書く。

### 手順どうしの関係は「順序」で片づけない

手順書は、ほかの手順書をよく参照する。その参照がすべて順序というわけではなく、次の3つに分かれる。

| 関係 | 例 | 書き方 |
| --- | --- | --- |
| 共通の部分手順を呼ぶ | 「配置したら稼働を確認する（完了の定義）」 | `depends_on`。前提である |
| 使い分けの分岐 | 「依存も変えたなら別の手順へ」 | `related`（相互に書く） |
| 失敗したときの退避先 | 「失敗したら復旧手順へ」 | 本文リンクでよい |

1つ目を本文リンクで済ませると、呼ばれる側を変えたときに、呼ぶ側が追従していないことに気づけない。「完了の確認」が別の手順書で定義されているなら、それは順序ではなく前提である。

判定は、ほかの層と同じである。その手順書が、参照先なしで完結するかどうかを見る。

## idを変えるとき

層を組み替えて接頭辞が変わった場合などでも、idは手で変えない。手で変えると、フロントマターのエッジ・本文の`[[ID]]`・目次の一覧・相対リンクのどれかを必ず落とす。

```bash
python -m tools.graph rename --from API-01 --to CON-01
```

新しい接頭辞が別の種別を指す場合は、`type`の書き換えとファイルの移動も同時に行われる。置き場所のディレクトリが決まらない`index`ノードは、`--path`で移動先を明示する。

```bash
python -m tools.graph rename --from IDX-API --to IDX-CON --path docs/40-contracts/index.md
```

本文の地の文までは直らない。「40-apiディレクトリ」のように、idでもリンクでもない記述は、自分で直す。`--dry-run`で影響範囲を先に見ておくとよい。

`rename`は、コードブロック・コードスパン・HTMLコメントの中を書き換えない。この文書に載せた使い方の例が、実行のたびに書き換わらないようにするためである（`check`がリンクを数えない範囲と同じ）。
