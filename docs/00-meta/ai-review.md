# 本文のレビュー（AI）

`check`が見るのは構造である。リンクが繋がっているか、依存の向きが正しいか、必須の節があるかを見る。**文章として読めるかどうかは見ていない。**

そこを人の代わりにAIに読ませるのが、`review`である。

```bash
python -m tools.graph review --limit 3
python -m tools.graph review --focus DOM-01
python -m tools.graph review --format json
```

## checkとは別物である

`check`と`review`を一緒にしてはいけない理由がある。

| | `check`（G001〜G023） | `review`（A001〜A009） |
| --- | --- | --- |
| 結果 | 同じ入力なら同じ結果 | 同じ入力でも変わりうる |
| 通信 | しない | する |
| 外部の鍵 | 要らない | `ANTHROPIC_API_KEY`が要る |
| 費用 | かからない | かかる |
| CI | 回す | 回さない |
| 終了コード | 問題があれば1 | 常に0 |

`G0xx`という番号は、「再現して、CIが強制するルール」という意味を持っている。再現しない指摘に同じ番号を与えると、番号の意味が成り立たなくなる。だから`A0xx`という別の名前空間にしてある。

`check`は、今までどおりオフラインで完結する。鍵を設定しても、`check`は通信しない。外部と通信するのは、`review`を呼んだときだけである。

## 指摘コード

| コード | 内容 |
| --- | --- |
| `A001` | 曖昧表現 |
| `A002` | 冗長表現 |
| `A003` | 用語の不統一（同じ意味のことを、用語表とは別の語で書いている） |
| `A004` | 必須説明の欠落・粒度の不揃い |
| `A005` | 「前提 → 本文 → まとめ」の構造が成立していない |
| `A006` | このノードが何を説明するものか不明瞭 |
| `A007` | 「Nつある」と書いた数が、直後の列挙の数と合わない |
| `A008` | まだ必要になっていない一般化を規定している |
| `A009` | 1つしか実装が無いのに抽象を置いている |

`A003`が要るのは、「同じ意味なら同じ用語」を`check`では確かめきれないからである（[META-01](./graph-rules.md)の`G013`）。`G013`が見るのは旧称の文字列だけで、しかも依存の向きにしか届かない。上位層や兄弟ノードは見えない。

`review`には、全ドメインノードの用語と意味を渡している。依存先には絞らない。絞ると、上流のノードが兄弟の用語を別の語で書いた揺れを見つけられない。たとえば、大会のノードが「棄権」を「辞退」と書いていた揺れである。渡す量は、いちばん多い派生で約4,000字になる。

`A007`は`check`には入れられない。`A007`が出るのは、「理由は3つある」と書いた直後の列挙が4行になっている場合である。あとから1行足したときに、数を直さなかったことで起きる。

機械的に当てはめると、誤検出が本物を上回った（実測で15件中11件）。「1つだけ試す」「1つある」のように、列挙の個数を指していない用法が多いからである。数えたうえで文意を見る必要があるので、`review`の側に置いてある。

`A004`（必須説明の欠落・粒度の不揃い）に含めることもできるが、専用の指摘として書いたほうが伝わるので、分けた。

### 過剰な設計（A008・A009）

YAGNI（まだ要らないものは作らない）という考え方を、設計文書に当てはめたものである。コードに入ってからではなく、文書が規定した時点で見つけるためにある。

| コード | 兆候 | 指摘しないもの |
| --- | --- | --- |
| `A008` | まだ無い要求のために、拡張点や切り替えの仕組みを規定している | 要る理由（受け入れ条件など）が本文から読める |
| `A009` | 差し替えられる仕組みを置いたが、本文が挙げる具体例が1つだけ | 契約が境界の約束を定めていること |

どちらのコードでも、次の2つは正しい書き方なので、対象外にしてある。1つはADRの「検討した案」「却下した案」で、案を並べるのはADRの仕事だ。もう1つは「やらない」「必要になったら足す」と先送りを明記した箇所で、過剰な設計を避けた記録であって、兆候ではない。

`A008`と`A009`も、`check`には入れられない。「将来に備えて」「汎用的に」のような語が出てくるだけでは、過剰とは言えない。要求が本当に無いかは、文意を読まないと分からない。

AIには断定させていない。送っているのは対象ノードの本文とドメインの用語だけで、依存先の本文は送っていない。そのため、要る理由が依存先にだけ書いてあると、誤って挙がる。その場合は、本文からそのノードを指せば挙がらなくなる。読む人にとっても、理由を本文から辿れるほうがよい。

## 何を送っているか

| 送るもの | 補足 |
| --- | --- |
| 対象ノードの本文 | フロントマターと自動生成ブロックを除く |
| `id`・`type`・`title` | |
| 全ドメインノードの用語 | 用語・意味・旧称。1.19までの「使ってはいけない言い換え」も含む |

送るのは1ノードずつで、グラフ全体は送らない。

既定では、10ノードまでしか送らない（`--limit`）。`--limit 0`で全件になるが、ノードの数だけAPIを呼ぶので費用がかかる。実行する前に、何件送るかを必ず表示する。

## 従う義務はない

`review`が出すのは助言であって、検査ではない。内容の正しさは判断できないので、書かれている事実は正しいものとして扱わせている。構造の誤りは`check`の担当なので、指摘させていない。好みの問題は指摘しないよう指示してあるが、完全には防げない。

**指摘が0件でも、品質の保証にはならない。** 逆に、指摘があっても、直す必要があるとは限らない。

## 鍵が無いとき

何もせずに終わる。グラフの問題ではないので、失敗にはしない。

```
ANTHROPIC_API_KEY が設定されていないため、レビューを行いません。
これはグラフの問題ではありません。check は影響を受けません。
```

## CIで回さない理由

| 理由 | 説明 |
| --- | --- |
| 再現しない | 同じコミットで通ったり落ちたりするCIは、信用されなくなる |
| 費用がかかる | pushのたびに、全ノードを送ることになる |
| 鍵が要る | 派生リポジトリごとに、シークレットの設定が必要になる |
| 通信する | `check`がオフラインで完結するという性質を失う |

必要なときに、人が手で回す。主な使い方は、書いている最中に1ノードだけ見てもらうことである。
