# 本文のレビュー（AI）

`check` は**構造**を見る。リンクが繋がっているか、依存の向きが正しいか、
必須の節があるか。**文章として読めるかどうかは見ていない。**

そこを人の代わりに読ませるのが `review` である。

```bash
python -m tools.graph review --limit 3
python -m tools.graph review --focus DOM-01
python -m tools.graph review --format json
```

## check とは別物である

**一緒にしてはいけない理由がある。**

| | `check`（G001〜G022） | `review`（A001〜A009） |
| --- | --- | --- |
| 結果 | **同じ入力なら同じ結果** | **同じ入力でも変わりうる** |
| 通信 | しない | **する** |
| 外部の鍵 | 要らない | `ANTHROPIC_API_KEY` が要る |
| 費用 | かからない | **かかる** |
| CI | 回す | **回さない** |
| 終了コード | 問題があれば 1 | **常に 0** |

`G0xx` という番号は「再現して、CI が強制するルール」という意味を持っている。
**再現しない指摘に同じ番号を与えると、番号の意味が壊れる。**
だから `A0xx` という別の名前空間にしてある。

**`check` は今までどおりオフラインで完結する。** 鍵を設定しても `check` は
通信しない。`review` を呼んだときだけ外に出る。

## 指摘コード

| コード | 内容 |
| --- | --- |
| `A001` | 曖昧表現 |
| `A002` | 冗長表現 |
| `A003` | 用語の不統一（同じ意味のことを、用語表とは別の語で書いている） |
| `A004` | 必須説明の欠落・粒度の不揃い |
| `A005` | 「前提 → 本文 → まとめ」の構造が成立していない |
| `A006` | このノードが何を説明するものか不明瞭 |
| `A007` | 「N つある」と書いた数が、直後の列挙の数と合わない |
| `A008` | まだ必要になっていない一般化を規定している |
| `A009` | 1 つしか実装が無いのに抽象を置いている |

`A003` が要るのは、**同じ意味なら同じ用語**を `check` では確かめきれないため
（[META-01](./graph-rules.md) の `G013`）。`G013` が見るのは旧称の文字列だけで、
しかも依存の向きにしか届かない（上位層、兄弟ノードは見えない）。

**`review` には全ドメインノードの用語と意味を渡している。** 依存先に絞らない。
絞ると、上流のノードが兄弟の用語を別の語で書いた揺れ（大会のノードが「棄権」を
「辞退」と書いていた、など）を渡しようがない。量はいちばん多い派生で約 4,000 字。

**`A007` は `check` に入れられない。** 「理由は 3 つある」と書いた直後の列挙が
4 行になっている、という形で、**あとから 1 行足したときに数を直さなかった**ときに出る。

機械的に当てると**誤検出が本物を上回った**（実測で 15 件中 11 件）。
「1 つだけ試す」「1 つある」のように、**列挙の個数を指していない用法が多い**ためである。
数えたうえで文意を見る必要があるので、`review` の側に置いてある。

`A004`（必須説明の欠落・粒度の不揃い）に含めることもできるが、
**専用の指摘として書いたほうが伝わる**ので分けた。

### 過剰な設計（A008・A009）

**YAGNI（まだ要らないものは作らない）を設計文書に当てたもの**である。
コードに入ってからではなく、**文書が規定した時点**で見つけるためにある。

| コード | 兆候 | 指摘しないもの |
| --- | --- | --- |
| `A008` | まだ無い要求のために、拡張点や切り替えの仕組みを規定している | 要る理由（受け入れ条件など）が本文から読める |
| `A009` | 差し替えられる仕組みを置いたが、本文が挙げる具体が 1 つだけ | 契約が境界の約束を定めていること |

**どちらのコードでも、次の 2 つは対象外にしてある。** 正しい書き方だからである。

- **ADR の「検討した案」「却下した案」。** 案を並べるのは ADR の仕事である
- **「やらない」「必要になったら足す」と先送りを明記した箇所。**
  過剰な設計を避けた記録であって、兆候ではない

**`check` には入れられない。** 「将来に備えて」「汎用的に」のような語が出てくる
だけでは過剰とは言えない。**要求が本当に無いかは、文意を読まないと分からない。**

**断定させていない。** 送っているのは対象ノードの本文とドメインの用語だけで、
**依存先の本文は送っていない。** 要る理由が依存先にだけ書いてあると、誤って挙がる。
そのときは**本文からそのノードを指せば消える。** 読む人にとっても、
理由が本文から辿れるほうがよい。

## 何を送っているか

- 対象ノードの**本文**（フロントマターと自動生成ブロックを除く）
- `id` / `type` / `title`
- **全ドメインノードの用語**（用語・意味・旧称。1.19 までの「使ってはいけない言い換え」も含む）

**送るのは 1 ノードずつ。** グラフ全体は送らない。

**既定では 10 ノードまでしか送らない**（`--limit`）。`--limit 0` で全件になるが、
ノード数だけ API を呼ぶので費用がかかる。実行前に**何件送るかを必ず表示する。**

## 従う義務はない

出てくるのは**助言**であって検査ではない。

- 内容の正しさは判断できない。**書かれている事実は正しいものとして扱わせている**
- 構造の誤りは指摘させていない。それは `check` の担当
- 好みの問題は指摘しないよう指示してあるが、**完全には防げない**

**指摘が 0 件でも品質の保証にはならない。**
逆に、指摘があっても直す必要があるとは限らない。

## 鍵が無いとき

何もせずに終わる。**グラフの問題ではないので失敗にしない。**

```
ANTHROPIC_API_KEY が設定されていないため、レビューを行いません。
これはグラフの問題ではありません。check は影響を受けません。
```

## CI で回さない理由

1. **再現しない。** 同じコミットで通ったり落ちたりする CI は信用されなくなる
2. **費用がかかる。** push のたびに全ノードを送ることになる
3. **鍵が要る。** 派生リポジトリごとにシークレットの設定が必要になる
4. **通信する。** `check` がオフラインで完結するという性質を失う

必要なときに人が手で回す。**書いている最中に 1 ノードだけ見てもらう**のが主な使い方である。
