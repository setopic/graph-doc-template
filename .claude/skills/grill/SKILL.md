# 要件を詰める

**曖昧なまま書き始めない。** 書いてから直すと、ADRが「決めた記録」ではなく、「揺れた記録」になる。

このスキルは、[mattpocock/skills](https://github.com/mattpocock/skills)の`grilling`を、このプロジェクトのグラフに合わせて作り直したものである。

骨格（決定木・ラウンド・frontier）は原典と同じで、違うのは次の3点だけである。

| | 原典の`grilling` | このスキル |
| --- | --- | --- |
| 事実の調べ方 | 環境一般（サブエージェントに任せる） | `tools.graph`の具体的なコマンド（下記） |
| 決まったことの行き先 | 規定なし | ADR・受け入れ条件・用語表（`G013`・`G022`が機械で見る） |
| 用語集 | `grill-with-docs`が`CONTEXT.md`を作る | 手で作らない。ドメインの目次の「用語の一覧」を`sync`が作る（下記） |

原典が入っていなくても動く。テンプレートは公開リポジトリで、`mattpocock/skills`を入れていない利用者がいるので、このファイルだけで完結させてある。**`Skill`の呼び出しに委譲しない。**

## 原則

1. 事実を調べるのはこちらの仕事で、利用者には聞かない。数えられるものは数え、「たぶん多い」のまま聞かない
2. 答えられる問いだけを聞く。ほかの未決の問いに依存する問いは、次のラウンドへ回す
3. 1ラウンド分をまとめて出す。番号を振り、それぞれに推奨案を添える
4. すべての枝が解決するまで終わらない
5. 合意できるまで、実装も文書化も始めない

## 進め方

### 1. 決定木を作る

要件から、決めなければ先に進めないことを洗い出し、依存の順に並べる。決定は、ほかの決定に依存する。何を先に決めるべきかが、ここで決まる。

### 2. 事実を先に調べる

聞く前に調べる。このプロジェクトでは、次のコマンドで調べられる。

```bash
python -m tools.graph render --format json --focus <ID> --depth 1
```

このコマンドは、近傍（前提と影響範囲）を最小の集合で返す。返ってきたノードだけを読む。

```bash
python -m tools.graph stats
```

実装が同じリポジトリにあるなら、`app/`も読む。`implemented_by`が付いているノードでは、指し先の実装が答えを持っていることがある。

測れるものは測る。このプロジェクトでは、測った結果によって判断が何度も覆っている。

| 測ったもの | 結果 | 何が変わったか |
| --- | --- | --- |
| 雛形の全節を必須にしたら | 141ノード中50件（35%）が落ちた | `G014`を、既存のノードのほぼすべてが持つ節に絞った |
| 「依存先のほうが新しい」で見たら | 212ノード中47件（22%）が常に該当した | `G015`を変更の窓だけに絞った |
| 全部入りのファイルを指したら | `bot.py`は90コミット中76件で変更されていた | `implemented_by`から外した |

**どれも、測らなければ「良さそう」のまま通っていた。**

時間のかかる調査は、サブエージェントに任せる。全文検索、実装の走査、gitの履歴の集計のように、答えが出るまで待つ必要があるものが対象である。

そして、調査の結果を待たない。調査中のものは「まだ片付いていない前提」として扱い、その調査に依存する問いだけを次のラウンドへ回す。残りのfrontierは、今のラウンドで聞く。調査1件のために、全体を止めない。

### 3. frontierを選ぶ

前提がすべて片付いている問いだけを選ぶ。「Aが決まらないとBは決められない」なら、Bは今回のラウンドに入れない。

### 4. まとめて聞く

1ラウンド分を、番号を付けて出す。それぞれに、推奨案とその根拠を添える。根拠は調べた事実であって、好みではない。

```
**Q1. <問いの見出し>**
<問いの本文。選択肢があるなら並べる>

推奨: <推奨案と、その根拠になった事実>

---

**Q2. <問いの見出し>**
...

推奨: ...
```

選択式のGUI（ウィザードなど）に差し替えてよい。大事なのは「1ラウンド分をまとめて出す」「各問に推奨案が付く」の2つで、表示の手段ではない。比較表や図が判断に役立つなら添える。

そのあとは回答を待つ。回答より先に書き始めない。

### 5. 繰り返す

frontierが空になるまで繰り返す。空とは、決定木のすべての枝を通り、断りなく仮定したものが1つも無い状態である。

### 6. 決まったことを文書へ移す

移す先は、META-07（`docs/00-meta/issue-pr-flow.md`）の「決まったことは文書へ移す」にある。まだ答えが無い問いは、issueに残す。

**却下した案は必ず書く。** ADRの価値の半分はそこにある。「なぜそうしなかったか」が残っていないと、同じ議論を繰り返す。

最後に検証する。`check`だけでは足りない。ノードを増やすと目次とREADMEの図が古くなり、CIはそこも確かめている。

```bash
python -m tools.graph sync
make readme
python -m tools.graph check
```

実際に1度、CIを落とした。ADRを1件足して`check`だけを回し、図を作り直さずにpushしたため、graph-checkが失敗した。

## CONTEXT.mdを手で作らない

元のスキルは、用語集を`CONTEXT.md`に集める。このプロジェクトでは、`CONTEXT.md`を手で作らない。

用語は、ドメインノードの「用語」表にある。手で集めると、検査のかからない写しが1つ増える。まとめて見る場所はすでにある。ドメインの目次（`docs/20-domain/index.md`）の「用語の一覧」を、`sync`が用語表から作り、最新かどうかをCIが確かめている。

決まった語を用語表へ移す前に、一覧で調べる。同じ意味の語がすでにあれば、それを使う（同じ意味なら同じ用語）。同じ字面の語が別のノードにもあれば、`G022`が警告を出す。言い換えは並べない。紛らわしい語との違いは「意味」の欄に書き、「旧称」には改名して使わなくなった語だけを書く。

同じ理由で、issueにも受け入れ条件を書き写さない。受け入れ条件は、ユースケースが持っている。

## やってはいけないこと

| やってはいけないこと | 理由 |
| --- | --- |
| 推奨案を添えずに聞く | 選択肢だけを並べるのは、判断を相手に返しているだけである |
| 依存している問いを、同じラウンドで聞く | 答えが噛み合わなくなる |
| 調べれば分かることを聞く | ノードの数、参照の数、実装の有無は数えられる |
| 決まる前に文書を書き換える | 揺れがADRに残る |
| 用語表に言い換えを並べる | 並べた語しか見つけられず、文脈で意味が変わる語ほど「禁止語に挙げない」という断り書きが増える。同じ意味なら同じ用語を使い、違いは「意味」の欄に書く |
| 旧称を足す前に、本文を検索しない | 使われている語を後から旧称にすると、正しい文章が大量に当たる。言い換えを禁じていた頃に、4回起きている |

旧称を足す前に検索するときは、自分の本文だけでなく、兄弟ノードの用語表（用語の一覧で調べられる）と、その兄弟に依存しているノードの本文まで見る。

## 終わる条件

- [ ] 決定木のすべての枝に答えがある
- [ ] 断りなく仮定したものが1つも無い
- [ ] 利用者が「これで合っている」と言った
- [ ] 決まったことが、ADR・ユースケース・ドメインノードに移っている
- [ ] `sync`と`make readme`を回した（ノードを増やしたなら必須）
- [ ] `check`が通る

**ほかの人の作業中の変更を巻き込まないこと。** 同じリポジトリを、別のセッションが触っていることがある。`git add -A`ではなく、自分が作ったファイルを名指しで足す。
