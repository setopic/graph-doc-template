# 要件を詰める

**曖昧なまま書き始めない。** 書いてから直すと、ADR が「決めた記録」ではなく
「揺れた記録」になる。

このスキルは
[mattpocock/skills](https://github.com/mattpocock/skills) の `grilling` を、
このプロジェクトのグラフに合わせて作り直したもの。

**骨格（決定木・ラウンド・frontier）は原典と同じ。** 違うのは 3 点だけである。

| | 原典の `grilling` | このスキル |
| --- | --- | --- |
| 事実の調べ方 | 環境一般（サブエージェントに任せる） | **`tools.graph` の具体的なコマンド**（下記） |
| 決まったことの行き先 | 規定なし | **ADR / 受け入れ条件 / 用語表**（`G013`・`G022` が機械で見る） |
| 用語集 | `grill-with-docs` が `CONTEXT.md` を作る | **手で作らない。** ドメインの目次の「用語の一覧」を `sync` が作る（下記） |

**原典が入っていなくても動く。** このファイルだけで完結させてあるのは、
テンプレートが公開リポジトリで、`mattpocock/skills` を入れていない利用者が
いるためである。**`Skill` 呼び出しに委譲しない。**

## 原則

1. **事実を調べるのはこちらの仕事。利用者に聞かない。**
   数えられるものは数える。「たぶん多い」で聞かない
2. **答えられる問いだけを聞く。** 他の未決の問いに依存する問いは次のラウンドへ回す
3. **1 ラウンド分をまとめて出す。** 番号を振り、**それぞれに推奨案を添える**
4. **すべての枝が解決するまで終わらない**
5. **合意できるまで、実装も文書化も始めない**

## 進め方

### 1. 決定木を作る

要件から「決めなければ先に進めないこと」を洗い出し、依存で並べる。
**決定は他の決定に依存する。** 何を先に決めるべきかがここで決まる。

### 2. 事実を先に調べる

**聞く前に調べる。** このプロジェクトで調べられるもの。

```bash
python -m tools.graph render --format json --focus <ID> --depth 1
```

近傍（前提と影響範囲）が最小の集合で返る。返ってきたノードだけを読む。

```bash
python -m tools.graph stats
```

実装が同じリポジトリにあるなら `app/` も読む。
**`implemented_by` が付いているノードは、指し先が答えを持っていることがある。**

**測れるものは測る。** このプロジェクトの判断は繰り返し測定で覆っている。

| 測ったもの | 結果 | 何が変わったか |
| --- | --- | --- |
| 雛形の全節を必須にしたら | 141 ノード中 50 件（35%）が落ちた | `G014` を経験的な中核に絞った |
| 「依存先のほうが新しい」で見たら | 212 ノード中 47 件（22%）が恒常的に該当 | `G015` を変更の窓だけに絞った |
| 全部入りのファイルを指したら | `bot.py` は 90 コミット中 76 件で変更 | `implemented_by` から外した |

**どれも、測らなければ「良さそう」で通っていた。**

**時間のかかる調査はサブエージェントに投げる。** 全文検索、実装の走査、
git 履歴の集計のように、答えが出るまで待つ必要のあるものが対象。

**そして待たない。** 調査中のものは「まだ片付いていない前提」として扱い、
**その調査に依存する問いだけ**を次のラウンドへ回す。
残りの frontier は今のラウンドで聞く。**調査 1 件で全体を止めない。**

### 3. frontier を選ぶ

**前提がすべて片付いている問い**だけを選ぶ。
「A が決まらないと B は決められない」なら、B は今回のラウンドに入れない。

### 4. まとめて聞く

1 ラウンド分を番号付きで出す。**それぞれに推奨案と、その根拠を添える。**
根拠は「調べた事実」であって、好みではない。

```
❓ **Q1** — **<問いの見出し>**: <問いの本文。選択肢があるなら並べる>

➡️ <推奨案と、その根拠になった事実>

---

❓ **Q2** — **<問いの見出し>**: ...

➡️ ...
```

**選択式の GUI（ウィザードなど）に差し替えてよい。** 大事なのは
「1 ラウンドぶんをまとめて出す」「各問に推奨案が付く」の 2 つで、
表示の手段ではない。比較表や図が判断に効くなら添える。

回答を待つ。**先回りして書き始めない。**

### 5. 繰り返す

frontier が空になるまで。**空とは「決定木のすべての枝を通り、
黙って仮定したものが 1 つも無い」状態。**

### 6. 決まったことを文書へ移す

| 決まったこと | 書く先 | 残るか |
| --- | --- | --- |
| まだ答えが無い問い | issue | 流れる |
| **なぜその判断にしたか、却下した案** | **ADR**（`new --type adr`） | 残る |
| 振る舞い、例外、受け入れ条件 | ユースケースの「受け入れ条件」 | 残る |
| 概念、言葉、不変条件 | ドメインノードの「定義」「不変条件」「用語」 | 残る |
| 実装 | ソース（`implemented_by` で指す） | 残る |

**却下した案を必ず書く。** ADR の価値の半分はそこにある。
「なぜそうしなかったか」が残っていないと、同じ議論を繰り返す。

最後に検証する。**`check` だけでは足りない。**
ノードを増やすと目次と README の図が古くなり、**CI はそこも見ている。**

```bash
python -m tools.graph sync
python -m tools.graph render --format mermaid --into README.md
python -m tools.graph check
```

**実際に 1 度落とした。** ADR を 1 件足して `check` だけ回し、
図を作り直さずに push して graph-check が失敗した。

## CONTEXT.md を手で作らない

元のスキルは用語集を `CONTEXT.md` に集める。**このプロジェクトでは手で作らない。**

用語は**ドメインノードの「用語」表**にあり、手で集めると
**検査の効かない写しが 1 つ増える。** まとめて見る場所は既にある。
ドメインの目次（`docs/20-domain/index.md`）の**「用語の一覧」**を `sync` が用語表から作り、
CI が最新かを見ている。

**決まった語を用語表へ移す前に、一覧で引く。** 同じ意味の語がもうあれば、それを使う
（同じ意味なら同じ用語）。同じ字面の語が別のノードにもあれば `G022` が鳴る。
**言い換えは並べない。** 紛らわしい語との違いは「意味」の欄に書き、
「旧称」には改名で使わなくなった語だけを書く。

同じ理由で、issue にも受け入れ条件を書き写さない。
**受け入れ条件はユースケースが持っている。**

## やってはいけないこと

- **推奨案を添えずに聞く。** 選択肢だけ並べるのは判断を投げ返しているだけ
- **依存している問いを同じラウンドで聞く。** 答えが噛み合わなくなる
- **調べれば分かることを聞く。** ノードの数、参照の数、実装の有無は数えられる
- **決まる前に文書を書き換える。** 揺れが ADR に残る
- **用語表に言い換えを並べる。** 並べた語しか捕まえず、文脈で意味が変わる語ほど
  「禁止語に挙げない」という断り書きが増える。同じ意味なら同じ用語を使い、
  違いは「意味」の欄に書く
- **旧称を足す前に、本文を検索しないこと。**
  使われている語を後から旧称にすると正しい文章が大量に当たる。
  **言い換えを禁じていた頃に 4 回やっている。**
  自分の本文だけでなく、**兄弟ノードの用語表（用語の一覧で引ける）と、
  その兄弟に依存しているノードの本文まで**見る

## 終わる条件

- [ ] 決定木のすべての枝に答えがある
- [ ] 黙って仮定したものが 1 つも無い
- [ ] 利用者が「これで合っている」と言った
- [ ] 決まったことが ADR・ユースケース・ドメインノードに移っている
- [ ] `sync` と `render --into README.md` を回した（ノードを増やしたなら必須）
- [ ] `check` が通る

**他人の作業中の変更を巻き込んでいないこと。** 同じリポジトリを別のセッションが
触っていることがある。`git add -A` ではなく**自分が作ったファイルを名指しで**足す。
