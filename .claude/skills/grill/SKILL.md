# 要件を詰める

**曖昧なまま書き始めない。** 書いてから直すと、ADRが「決めた記録」ではなく、「揺れた記録」になる。

このスキルは、[mattpocock/skills](https://github.com/mattpocock/skills)の`grilling`を、このプロジェクトのグラフに合わせて作り直したものである。

原典が入っていなくても動く。テンプレートは公開リポジトリで、`mattpocock/skills`を入れていない利用者がいるので、このファイルだけで完結させてある。**`Skill`の呼び出しに委譲しない。**

## 原則

1. 事実を調べるのはこちらの仕事で、利用者には聞かない。ノードの数、参照の数、実装の有無は数えられる。数えられるものは数え、「たぶん多い」のまま聞かない
2. 答えられる問いだけを聞く。ほかの未決の問いに依存する問いは、次のラウンドへ回す。同じラウンドで聞くと、答えが噛み合わなくなる
3. 1ラウンド分をまとめて出す。番号を振り、それぞれに推奨案を添える。選択肢だけを並べるのは、判断を相手に返しているだけである
4. 決定木のすべての問いに答えが出るまで終わらない
5. 合意できるまで、実装も文書化も始めない

## 進め方

### 1. 決定木を作る

要件から、決めなければ先に進めない問いを洗い出し、依存の順に並べる。問いは、ほかの問いの答えに依存する。何を先に決めるべきかが、ここで決まる。

### 2. 事実を先に調べる

聞く前に調べる。このプロジェクトでは、次のコマンドで調べられる。

```bash
python -m tools.graph render --format json --focus <ID> --depth 1
```

このコマンドは、近傍（前提と影響範囲）を最小の集合で返す。返ってきたノードだけを読む。

```bash
python -m tools.graph stats
```

実装が同じリポジトリにあるなら、実装のディレクトリも読む。`implemented_by`が付いているノードでは、参照先の実装が答えを持っていることがある。

測れるものは測る。たとえば、ルールを足す前に、既存のノードのうち何件が当たるかを数える。`implemented_by`でファイルを指す前なら、そのファイルが何コミットで変わったかを見る。測らないと、「良さそう」という見込みのまま判断が通ってしまう。

時間のかかる調査は、サブエージェントに任せる。全文検索、実装の走査、gitの履歴の集計のように、答えが出るまで待つ必要があるものが対象である。

そして、調査の結果を待たない。調査中のものは「まだ片付いていない前提」として扱い、その調査に依存する問いだけを次のラウンドへ回す。残りのfrontierは、今のラウンドで聞く。調査1件のために、全体を止めない。

### 3. frontierを選ぶ

前提がすべて片付いている問いだけを選ぶ。「Aが決まらないとBは決められない」なら、Bは今回のラウンドに入れない。

### 4. まとめて聞く

1ラウンド分を、番号を付けて出す。それぞれに、推奨案とその根拠を添える。根拠は調べた事実であって、好みではない。

問いは、「はい」と答えれば推奨案を選んだことになる書き方にする。利用者が推奨案に同意するだけなら、1語で答えられる。

```
**Q1. <問いの見出し>**
<問いの本文。選択肢があるなら並べる>

推奨: <推奨案と、その根拠になった事実>

---

**Q2. <問いの見出し>**
...

推奨: ...
```

選択式のGUI（ウィザードなど）に差し替えてよい。「1ラウンド分をまとめて出す」「各問に推奨案が付く」の2つが大事で、表示の手段は問わない。比較表や図が判断に役立つなら添える。

そのあとは回答を待つ。回答より先に書き始めない。

### 5. 繰り返す

決定木のすべての問いに答えが出るまで繰り返す（下の「終わる条件」）。調査の結果を待っている問いが残っているなら、そのラウンドのfrontierが空でも終わらない。

### 6. 決まったことを文書へ移す

移す先は、META-07（`docs/00-meta/issue-pr-flow.md`）の「決まったことは文書へ移す」にある。まだ答えが無い問いは、issueに残す。

**却下した案は必ず書く。** ADRの価値の半分はそこにある。「なぜそうしなかったか」が残っていないと、同じ議論を繰り返す。

最後に検証する。`check`だけでは足りない。ノードを増やすと目次とREADMEの図が古くなり、CIはそこも確かめている。

```bash
make all
python -m tools.graph check
```

`make all`は、`check`・`sync`・`linkify`・`make readme`を、CIと同じ引数で回す。`sync`と`linkify`は文書を書き換えるので、そのあとにもう一度`check`を回す。

## 決まった語を用語表へ移す

決まった語は、ドメインノードの「用語」表に書く。書く前に、ドメインの目次（`docs/20-domain/index.md`）の「用語の一覧」で、同じ意味の語がすでに無いかを調べる。用語表の書き方（言い換えと旧称の扱い）は、CLAUDE.mdの「文書を書くときの前提」にある。

受け入れ条件はユースケースに書き、issueには書き写さない。

## 終わる条件

- [ ] 決定木のすべての問いに答えがある
- [ ] 断りなく仮定したものが1つも無い
- [ ] 利用者が「これで合っている」と言った
- [ ] 決まったことが、ADR・ユースケース・ドメインノードに移っている
- [ ] `make all`を回した
- [ ] `check`が通る
